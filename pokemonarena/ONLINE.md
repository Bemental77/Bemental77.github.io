# Pokemon Arena online: battle a friend

Two people, two devices, one battle. Nothing is streamed and nothing runs on a server: **both browsers run the same deterministic engine, and only the two
players' choices cross the wire**, which is how every other online page on this site works (every machine runs the game; the missing input is waited for,
never guessed; a state hash that disagrees stops the session and names the turn).

## How to play

* **From the hub:** the "Play online" link under the menu opens `/pokemonarena/battle.html?online=1`, which shows the list of **open games** (below). The **Open** switch beside it makes *you* challengeable while you use the rest of the Arena.
* **From the lobby** (`/multiplayer.html`): pick *Pokemon Arena*, *Open a party*, give your friend the code (it starts with `A`) or the invite link, press *Start my console*.
  A friend who types only the code is taken to the Arena without being asked.
* **Direct:** `battle.html?np=CODE&host=1` and `battle.html?np=CODE&join=1`, `&team=<ARENA1 code>` preselects a team, `&format=6v6|3v3` is the host's default format.

Each player picks a saved team, a random team or a pasted team code, a name, and (the host) the format. The host's browser shows the code once the room is open and
asks the host to **allow** the joiner (a four-character confirmation code to read out, from `lib/netplay.js`). Then both browsers check each other's team, agree a
seed, and the team preview starts.

## What is reused and what is new

| Concern | Where |
|---|---|
| Pairing, room code, the host's approval, ICE and the relay fallback, link health | `lib/netplay.js` (`Netplay.Session`), unchanged |
| Our messages | type `lsarena` on that session's channel: sent with `session._send()`, received by wrapping `session._onRoomMsg` (the same seam `gba.html` uses for `lsgbahostbye`); the direct channel and the relay both end in that router |
| The protocol (handshake, seed, commit-reveal, hashes, clocks, rematch, resync) | `js/netmatch.js`: pure, no DOM, no network, no timers |
| Arena glue (judge a team code, build the controller for one side, fingerprint the engine) | `js/online_match.js`: pure |
| Setup panel, session, status bar, hand-off to the scene | `js/online.js` |
| The scene on side 1 for the guest, the `wait` screen ("Waiting for the other player...") | already in `scene.js` (`viewSide`) |
| `Battle.concede(side)` / `ctl.concede(side)` | `engine.js`, `matchctl.js`: a side leaves even while waiting with a real choice already in (a plain forfeit cannot: a real choice is final) |

**Why not the emulators' frame-lockstep engine** (`Lockstep` in `lib/netplay.js`)? It exists for cores that must run every frame at 60 Hz. A battle is turn based: a frame
loop would tick 30 times a second through five minutes of somebody thinking, and a backgrounded tab (timers throttled to 1 Hz) would turn every choice into seconds.
This protocol is message driven, so a hidden tab costs nothing.

## The protocol (`netmatch.js`)

Every message is `{ t:'lsarena', v:2, k, mn, ... }`; `mn` counts rematches. Every inbound message is shape-checked (`checkMessage`) before anything reads it. **The version is 2 since the 6v6 lead preview** (a 6v6 match now opens with a round that the build before it never ran): a message of any other version is refused as `version` ("The other player is on a different version of the Arena. Reload the page on both sides and try again."), the refuser tells the other side (`bye`: `version`), and no battle is built. The reload record in `sessionStorage` carries the same number, so a record saved by the older build is not replayed (`nm.resume` refuses it by name; `online.js` ignores it and shows the setup form).

| kind | from | meaning |
|---|---|---|
| `hello` | both | ROM sha-256, engine fingerprint, ruleset, name, team code, the host's format. Refused **by name** for a different ROM, a different engine build, different rules, an illegal team, a team too small for 3v3, a format named by the guest |
| `seedc` `seedb` `seedr` | host, guest, host | the shared seed: the host commits to its half, the guest answers with its own, the host opens. `seed = mix(a, b)`: the host is bound before it sees `b`, the guest never sees `a` until `b` is fixed |
| `go` | both | hash of the freshly started battle; both must agree before turn 1 |
| `rdy` | both | "my screen can take a choice": the other side's clock starts here, not while the last turn is still animating |
| `commit` `reveal` | both | a round where **both** sides choose (every turn, the 3v3 team preview, the 6v6 lead preview): `commit = sha256(room#match, round, side, choice, nonce)` with the state hash the round opened on; the choice is opened only after **both** commitments are in |
| `choice` | both | a round where only **one** side chooses (a replacement after a faint; the lead preview when the other team has one Pokemon and so is not asked): nothing to hide, so no commitment |
| `bye` `end` | both | leaving (the leaver forfeits) / the match is over, with the final hash |
| `rematch` | both | both must ask; then the seed handshake runs again with the same teams |
| `sync` | both | after a dropped link or a reload: "I am here, resend me from round N" |

**Rounds** are numbered identically on both machines (a round opens each time the engine has advanced and someone has a choice to make). A round is applied only when
everything it needs is verified: the commitment opens correctly, the choice is legal (`ctl.submitRemote` is the engine's own `choose`), and the opening state hash equals ours.

### The 6v6 lead preview

A 6v6 match opens with a **lead round**: each player chooses which of their Pokemon is sent out first (`createBattle({ lead: true })`; the choice is a one-slot preview, `{ kind: 'preview', order: [slot] }`, one 16-bit word like every other choice, so the protocol needed no new message kind; the rest of the team follows in team order). It is an ordinary both-choose round (the `preview` phase of the engine, `round.kind` `preview`, the 3-minute preview clock): the two leads are **committed and revealed together**, so the player who chooses first is not seen (`pokemonarena_netmatch_test.mjs` case S sends the first commitment and checks that nothing but a digest crosses until the other one arrives; the page test `lead` checks that the other tab's engine and log hold no trace of the lead). A side whose team has **one** Pokemon is not asked (the engine marks it automatic): the other player's lead then travels as a plain `choice`, and two teams of one have no lead round at all. A lead that names a Pokemon the player does not have, two Pokemon, or a move is `illegal` and stops the match; a lead revealed that is not the one committed is `cheat`. A reload around the lead round comes back to the same question (case S reloads each player at each of the first twelve steps, with and without the messages in flight).

### No free-switch question online

The Gen 3 trainer-battle question "Will you switch your Pokemon?" (`ENGINE.md` `freeSwitch`) is asked only of a human seat that fights a CPU. `online_match.js buildNetController` never passes the option and `matchctl.js` offers it to no seat whose opponent is not a CPU, so an online battle's state has no `fs` key, no request is ever `reason: 'free'`, and the new `stay` choice (wire word 7) is never sent: a `stay` word on the wire in an ordinary round is refused by the engine as `wrong-phase` like any choice out of turn. (`pokemonarena_switch_test.mjs` plays 8 online matches through both machines' controllers and checks all of that.) The protocol version is unchanged by it.

### Clocks and leaving

| situation | result |
|---|---|
| the player forfeits (pause menu) or presses BACK TO HUB | they lose at once; the other side's scene shows the forfeit |
| the player's page is closed or reloaded | the link drops, the other side is told and waits (below); a RELOAD picks the battle up again |
| a player's screen is ready and they take longer than 2:00 (3:00 at the team preview) | they time themselves out; the other side's clock (+3 s) is the fallback if their page is frozen |
| a player's screen never becomes ready (a hidden tab) | out after 5:00 from the round opening |
| both committed and one reveal never comes (a broken or hostile client) | out after 30 s |
| the link drops (a closed page, a lost connection) | 60 s of grace; on reconnection the `sync` below resends exactly what was missed; after 60 s the player who stayed wins. A page that was reloaded into a battle and never gets back to the other player is stopped, and does not claim the other player left |
| an **abort** (desync, cheating, an illegal choice, a malformed message) | nobody wins; both pages say why |

A claim **against you** (a message that names you as the loser) is believed only when your own clock or link record agrees, and an honest peer has only two reasons to give for one:
`timeout` ("you timed out") and `lost-link` ("your link was dead"). Any claim against you is checked, **whatever label the sender put on it**: a `forfeit`, a `left`, a `closed` or any other
word of up to 24 characters about *you* is refused, and the match is stopped (`cheat`; nobody is scored, nothing is written). A claim against the sender itself (it forfeits, it leaves)
only ever hurts the sender, so it is simply taken. (`pokemonarena_netmatch_test.mjs` case H sends seven labels.)

## Reloads and dropped connections

* **A reload does not lose the battle.** After every change `online.js` keeps the match's `snapshot()` in `sessionStorage` (per tab; never sent anywhere): the agreed seed, every choice the engine has taken, the round, the hash the round opened on, the commitment's nonce, and every message sent this match. A page that is **reloaded** (the browser says `reload` or `back_forward`; opening the address afresh never resumes) rebuilds the controller from the seed, replays the recorded choices, **refuses unless that lands on the recorded state hash**, replays the scene silently and at speed, and re-syncs: its `sync` makes the other side resend what it missed, and its restored message log answers theirs. The address is rewritten to `?np=CODE&host=1|join=1` when a room is opened, so a reload finds its record. The record also names the **profile whose team the player chose** (`profileId`), so a battle finished after a reload is written to that career: the career's own search for a team code would otherwise find the active profile first, and a copy of the same team in another profile would win.
* **A resume that cannot be done** (a team that no longer checks out, a browser that cannot connect) shows the setup form once, with the reason on the screen.
* **The guest reloading** is re-admitted by the host with no prompt (`lib/netplay.js` remembers the seat). **The host reloading** makes the guest knock again by itself, and the host is asked once to allow it.
* **A dropped connection heals by itself:** `lib/netplay.js` re-knocks a link that was open and died (the room has not "started", so its normal rule applies); `online.js` also replaces a session that failed outright, on a timer, while the match's own 60 s clock runs.
* **Proved by:** `pokemonarena_netmatch_test.mjs` case R reloads each player at *every step* of three real matches, with nothing in flight, with the unsent messages lost, and (the case that found a real bug) with the player having answered but the answer not yet delivered; each must end in the uninterrupted match's exact final position (171 cases), plus records that must be refused by name; and `pokemonarena_online_page_test.mjs` group `rejoin` reloads the guest and the host in real Chrome tabs (same position on return, link back up without a click, the match plays on to the end in agreement), cuts a live connection, and checks that a fresh visit does not resume.
* **Limits:** the record is per tab (a different tab or browser starts over); a reload during the handshake (before turn 1) is not resumable; closing the tab for good costs the other player up to 60 s before they win.

## Open games, and being open while you play

Playing a friend needs a code. Playing *anyone* needs somewhere to see who is waiting. The site has no server, so the "notice board" is one more topic on the public MQTT-over-WebSocket brokers that `lib/netplay.js` already pairs through (`pokemonarena/js/openlobby.js`; the same-browser transport uses a BroadcastChannel). **Nothing is retained**: a game is on the board only while its beacons (every 4 s) keep arriving, and falls off 13 s after the last one, or at once when its owner leaves.

**On the battle page's panel (`?online=1`):**

* **Open games** lists everyone waiting, longest first, each with the format, the trainer's online record when they have one, and a **Join** button. One press joins: an open game lets the first player who asks in without the host pressing Allow (that is what *open* means), and **the moment it has let somebody in it comes off the board** and the host is told *a player is joining* (not "your game is open: anyone can join it"), not when the link finally comes up. If that player never connects, the seat is free again: the game is listed again and says it is open again. A player who knocks AGAIN under the same identity (a reloaded page) does not put the game back on the board while they are being let back in: `lib/netplay.js` tears the old link down (`peer-left`, reason `peer-reloaded`) and re-admits them by itself, **without asking the page**, so the page holds the seat and gives it up only when the library gives up on the link, or when no link has appeared for that player 10 s after the knock (their page may be gone). The player who is in is recorded from the library's own events, by the id they knocked with (`peer-joined`; a player the library re-admits by itself is noticed by its `room` event), so a host whose Session had to be rebuilt in the middle of a match lets that player back in with no prompt, even if the library had re-admitted them by itself after a first attempt failed, and still tells a genuine third player the game is taken. Games on another build of the engine are hidden (the handshake would refuse them by name) and **counted, whether or not other games are on show**. The list is updated **in place**, row by row: a keyboard, switch or pad user who is on a Join button keeps their place when another game appears, changes or expires, and a row that leaves hands the focus to the one that took its place (the list used to be rebuilt from nothing at every beacon). Join, Challenge and Find a battle are **one at a time**: a second press while the first is still reading your team (a double tap, Join while Find a battle is looking) is ignored, where it used to start a second connection and leak the first. A join that is waiting for its host shows **Cancel**, and says how long it can wait (a made-up game is given up on after 40 s). When a join from the list ends without a match (Cancel, a game that never answered, one that was taken) the address goes back to the plain Play online page (`?online=1`; joining had rewritten it to `?np=ROOM&join=1` so that a reload finds the room), so a reload shows the board and not the join-by-code form with the dead room filled in. A page that was opened with a room in its address (the lobby's hand-off) keeps that address.
* **Find a battle** joins the game that has waited longest, or, if nobody is waiting, opens one and waits. If two players press it together, both open a game and the one with the **larger room code joins the other** (one stays: both see both). The board is public and anyone can publish a beacon, so a rival counts only once its listing has been **heard twice, a beacon interval apart** (one made-up beacon moves nobody), only if it is a real room (not a resident label), and among several the **smallest code** is the one everybody goes to. If the join fails (the rival was made up, or somebody got there first) the rival is left off the board for two minutes, **no rival at all moves the player again for two minutes, whatever its room code** (remembering only the failed room let a forger that rotates its code be believed again 4 s after each new one), and **the player's own game is opened again automatically**: they end up listed, not at the setup form.
* **Open to anyone** (a switch on Host) lists your game. If the opponent never gets as far as a battle (they leave, or their ROM or engine does not match) your game goes back on the board under a new code instead of ending.
* A **private** game (a code you hand over) is never listed and still asks you to press Allow. (The plain Play online page, with no code in its address, dials the public brokers as soon as it opens, to read the board, whatever you go on to do; see **What is public**. Until a game is listed or a challenge sent it publishes only an anonymous "who is open?" request.) A game with a code that you host or join from that page lets go of the board when it starts.

**Open to battles (the hub's **Open** switch).** A battle against a person needs a room, and only the battle page can open one, so a player in the hub is listed as a **resident** game (`h:1`: a label, not a room) and is *challenged* instead of joined:

```
challenger (Open games)                owner (the hub or a CPU battle)                      owner's battle page after Accept
chal { to, r, name, rec, pk }  --->    a dialog: "<name> wants to battle you"
                           <-------    ok  { r }            Accept: "I am coming"  (writes the accept token, then navigates to battle.html?auto=host&for=..&rq=r)
                           <-------    dec { r, why }       Not now / busy / no answer
can { r }  --------------->            the dialog closes
                           <------------------------------------------------------   acc { to, r, pk, iv, ct }   (every 2 s until they are in)
```

`pk` is a **one-time ECDH P-256 public key** the challenger makes for this challenge (WebCrypto; the private half never leaves its page). The owner's battle page makes its own one-time key pair, derives an AES-GCM key from the two (ECDH, then HKDF-SHA-256 with a fixed label), and sends the room **sealed**: `pk` (its public key), `iv`, `ct` (the room, bound to this request id and this challenger by the cipher's additional data). **The room code is never on the board in the clear**; only the challenger can open `ct`. A browser without WebCrypto (it needs a secure context: HTTPS, or localhost) cannot challenge and says so; there is no fallback to the clear. `checkBeacon` refuses a challenge with no key and a "come in" with no sealed room, and only the fields the board defines are put on the public topic, so a stray field cannot carry a room along.

**An address does not start a game.** When the owner presses Accept, `presence.js` writes a **one-time token** into *that tab's* `sessionStorage` (`arena.accept`: the challenger's id, the request id, the challenger's key, the time) before navigating. The battle page hosts an accepted challenge only if it can take a token that matches `for` and `rq` and is under 2 minutes old, and taking it removes it. Any other way of arriving at `battle.html?online=1&auto=host&for=..&rq=..` (a link from anywhere, Back, a restored tab, the address pasted again) has no token: the ordinary online panel shows with a one-line notice, no room is opened and nothing is announced. If the token cannot be written (no `sessionStorage`) Accept tells the challenger *busy* instead of sending anybody anywhere. Once the room is open the address becomes `?np=ROOM&host=1` (`auto`, `for`, `rq`, `ck` dropped), so a **reload of the accepted-challenge page resumes the battle in the same room** like any host (the returning player is asked about once, as for any host) and does not open a second room.

The switch is one setting of this browser (`localStorage` `arena.open`, followed by every hub and CPU-battle tab through the `storage` event: switching it on or off in one reaches all of them, because a battle against the CPU mounts the page half in every case (a Pokemon Tower floor is the one exception: it does not mount it, because Accepting a challenge would leave the fight, which the Tower counts as a loss; a challenge reaches you in the hub, between floors) and keeps it **dormant** while the switch is off (no board connection, no dialog in the page), so a CPU-battle tab opened before the switch went on follows it too; the listing is read again from the profile when a tab comes back to the front, is restored from the back/forward cache, or the hub empties the record with RESET RECORD, and a read that fails (a store that cannot be opened) changes nothing instead of listing you as "Player"; the team builder and the online pages never list you). A battle against the CPU shows the switch as an **Open** icon button at the end of its header (green while it is on; pressing it switches the listing on or off from there; Tab reaches it like the other header buttons; it is not a row of the pause menu, so a controller-only player switches the listing off from the hub). The accessible name of the hub's switch and of that button is always "Open to battles", with pressed / not pressed saying the state. While it is on, the dialog reaches you in the hub *and* in the middle of a battle against the CPU (it pauses the battle like the Controls panel; Accept leaves it, and a battle left unfinished is recorded as nothing). The dialog is above every other dialog of the page and the page stays paused until the last of them has closed; its default button is **Not now** (B, Escape, X and Backspace press it), Accept is disabled for its first 600 ms and, if the focus only drifted onto it (a key that was already held, repeating), ignores the keyboard and the pad until a fresh press (also when the challenge is stacked over the Controls dialog or the Sound panel, whose own navigation moves the focus first: the guard reads the repeat, not who moved the focus), one dialog is shown at a time (a second challenger is told *busy*), at most 6 per minute, somebody told no is told no again quietly for 20 s, and a dialog nobody answers closes after 25 s and counts as a no. The page that opens after Accept picks the first saved team of the active profile (or a random team), opens a room, and tells the challenger the room (sealed to the challenger's one-time key, by the request id); the first player to knock is let in. The room code is known to the two of them only (it is on the owner's screen and in the address, never on the board), so "the first to knock" is in practice the challenger; a second knocker is told the game is taken.

**What is public.** The first time a player switches *Open* on, a dialog says what follows and asks (OK / Cancel; the answer is remembered in `arena.open.seen`) before anything is published; a stored "on" nobody was told about is not honoured. (The same-browser test transport publishes nothing anywhere and skips the dialog unless the address says `?opendisc=1`.) Switching *Open* on, or listing a game, puts your **trainer name, the format and (if you have one) your online record** on third-party public brokers, readable by anyone who subscribes. **So does a challenge you send from Open games** (`chal`: your trainer name, your online record if you have one, and a one-time public key; never a team or a room). **And merely opening the plain Play online page connects you to those brokers** (the board dials all five: shiftr.io, TBMQ, EMQX, Mosquitto, HiveMQ) and loads `mqtt.js` from cdnjs.cloudflare.com, whatever you do next: they can see your IP address and an anonymous "who is open?" under a random per-page id. The panel says all of this on screen (the Open games section, and beside the Open-to-anyone switch, which names the trainer name *and* the online record; the hub's Open switch asks first, naming both, before it publishes anything), not only here. The record is the online record of the profile that owns the **saved team** you chose; a random, pasted or address team has no owner in the panel, so it carries **no record** and the panel does not even open the browser's storage for it. Nothing else is published: no team, no profile, no address. (The team you PLAY goes to your opponent in the handshake, directly or, when there is no direct path, over `lib/netplay.js`'s relay; it is not part of anything the board publishes.) A room code in a listed game is public by design. **The room of an accepted challenge is not**: it is never on the board in the clear (see the diagram above); all the board learns is a challenge's one-time public key and a sealed message it cannot open. Closing the page, or switching off, takes the listing down at once (best effort; the board drops it 13 s later regardless).

**Everything on the board is advice.** Anyone can publish anything on a public broker, so every message is shape-checked, names are reduced to ASCII safe text, the list is capped at 24 games, one sender keeps one room, a flood is cut off, and the listing a player sees is always re-checked by the real pairing: a made-up game simply finds nobody (the joiner gives up after 40 s and leaves it off the list for 30 s), and a made-up room code is still gated by the room-key proof and the host's admission. What a stranger *can* do is show a game that is not there, send you a challenge dialog (rate-limited, default *Not now*), or make a waiting Find-a-battle host try a game that is not there (it takes two beacons a beacon interval apart; the cost is a failed join: the host's own game is off the board for the 40 s the join waits, then it is open again, the made-up game is left off the board for two minutes, and **no rival at all, whatever room code or sender it uses, moves that host for two minutes**). **What that does not prevent, honestly:** a forger that keeps publishing a fresh made-up game for as long as a player keeps waiting through Find a battle can still cost them one such 40 s absence about every 160 s (roughly a quarter of their time on the board), because nothing on a public, unauthenticated board can tell a forged listing from a real one before it has been tried. Its cost before the cooldown existed was about 40 s of every 44, because only the failed room code was remembered. It cannot touch a host that is not waiting through Find a battle, one that has already let somebody in, or one in a match, the host's game always comes back listed, and a friend who has the room code is not affected. What a stranger **cannot** do is learn the room of an accepted challenge, or turn a link into a hosted game (the accept token, above). **A known limit:** the sealing hides the real room from everyone, but it does not *authenticate* the owner: a stranger who read a challenge (it is public, and carries the challenger's public key) can seal a pointer to **their own** room, and the challenger will try it. They would meet a stranger's name in the handshake and the stranger's admission, never the real owner's room, and the challenger's own timeout ends the attempt; there is no pre-shared secret on a public board to do better with.

**Limits.** A tab that is hidden has its timers slowed by the browser, so a hidden hub tab may flicker off the board; the switch needs the hub (or a CPU battle that is not a Tower floor) page to be open, because a closed page cannot hear a challenge. Two players need to share at least one of the five public brokers (the board dials all of them). A board that loses every broker says "connecting" for 10 s and then "down" (and "up" again as soon as one comes back): the host of a listed game is then told nobody can find it, and Find a battle will not open a game it cannot show to anyone. Not tested on real phones or across two real networks. The suites use the same-browser transport and in-memory brokers; the real public-broker path has its own opt-in check (`node tools/pokemonarena_openlobby_live.mjs`), which talks to the real brokers.

## What it guarantees, and what it cannot

* Two honest machines cannot disagree: the engine is deterministic and the final position hashes are compared. A bug, a cached older script or a tampered client becomes a stopped match with a turn number.
* Neither player can read the other's choice before making their own, and neither can steer the dice (commit-reveal on both).
* A different ROM, engine build, ruleset or illegal team is refused by name before turn 1; hostile names are reduced to safe text identically on both machines.
* **It cannot hide the other team from a modified client.** Both engines need both teams to run (the cost of every lockstep game). The Stadium-style preview that hides the unchosen three is a presentation.
* **It cannot stop a player from aborting a match they are losing** (they can send an abort): such a match is stopped, nobody wins, and **nothing is written to either record**. Matches are unrated.
* The relay path (`lib/netplay.js` falls back to an MQTT relay when no direct path exists) carries a battle the same way; it has been tested with the same-browser transport only, not across two real networks.

## The profile: an online battle is part of your record

An online battle is kept in the trainer's profile like a battle against the CPU (`js/battle_boot.js` `recordCareer`, the same `store.recordMatch` write), from schema **4** of the profile (`js/career_stats.js`, `js/profile.js`):

* **Which profile.** The one that owns the team chosen in the setup panel (the panel lists saved teams per profile, and picking one fills in that trainer's name unless you typed your own), else the one that owns the team code, else the profile that is *active* in this browser. With no profile nothing is written and the recap says so. A battle finished after a **reload** goes to the same profile (the tab's record names it). **The name:** only a name you *typed* is remembered for the next visit, and it then stays when you change team; a name the panel filled in from a team's owner is not remembered, so the next visit starts with the owner of the pre-selected team.
* **What is written.** The result as the engine says it (a win, a loss, a draw), the turns, the highs, the totals and the favourites like any other battle, and it counts in the overall win rate and streaks. It has its own row, **ONLINE**, in the MODES page of the Record screen (shown once there is one), whose WIN RATE line then reads `CPU x%  ONLINE y%` (the three CPU levels together: four names with their rates do not fit the cell; with no online battle it is the rate per CPU level, as before), and the RECENT list says `ONLINE` and `VS <the other player's name>`. It is **never** counted under EASY / NORMAL / HARD.
* **Who is recorded as what.** The player who *forfeits* (RUN, YES), whose own clock runs out while the page is still open, or who comes back after a dead link that outlasted the 60 s grace is recorded as a **forfeit** (QUIT on the Record screen, not a loss); the one who stayed wins. **A player who leaves with BACK TO HUB, or closes the page, records nothing for themselves**: the page navigates 60 ms after it sends the goodbye, long before the scene has played the forfeit through to the result screen (the write happens there). The one who stayed still records the win. This is the same as leaving a battle against the CPU, which also records nothing.
* **A win the other player handed over** (they left, ran out of time, lost their link or forfeited) is a win in every counter, but it is **never your FASTEST WIN**, and a **walkover** (no second turn had begun when they left: 0 or 1 turns) is not your LONGEST BATTLE either: those HIGHS come from battles that were played. The rule counts turns, not moves: the usual walkover is a battle in which nothing was played (they left at the team preview or at the first choice), but one who leaves at the replacement prompt that follows a first turn in which a Pokemon fainted also concedes at 1 turn, with a move already used, and is a walkover too (no number can be hurt by it: a 1-turn battle can only beat a longest battle of 0 turns). Without this the first stranger to close the page at the team preview wrote "FASTEST WIN 0 TURNS", which nothing can ever beat. (`career_stats.js`: `conceded`, `isWalkover`, `WALKOVER_MAX_TURNS`; proved in `pokemonarena_career_test.mjs` and, with the real protocol, `pokemonarena_netmatch_test.mjs` case O.)
* **Once.** The match id is the seed, the format, the match number and the first 8 characters of the room code (`<seed>_<fmt>_o<n>_<ROOM>`, `career_stats.onlineMatchId`). A page that is reloaded into the match computes the same id as the machine that never reloaded, and an id that is folded twice changes nothing, so the same match cannot be counted twice; a rematch (a new number and seed), another room or another seed is a battle of its own. Proved in Node (`pokemonarena_netmatch_test.mjs` case O reloads the host in the middle of a rematch and compares the ids, then folds the match twice); the real-Chrome page test says it twice with real tabs: group `profile` reloads at the result screen (the setup form is back and the record is unchanged, F14), and group `resume` (RS1 to RS10) reloads the HOST's page in the middle of a match with a saved profile on each side, plays the match to the end, and reads both stored profiles: each holds EXACTLY ONE online battle, it is the same match id on both, it is the id the match had before the reload, and nothing is written a second time afterwards (checked by running the group against a copy of the game in which a resumed match gets another seed: RS3, RS7 and RS8 fail). Leaving from the result screen waits (at most 1.5 s) for the write.
* **Never for a stopped match.** A match that was stopped (a desync, a cheat, a malformed message, a refused team) writes nothing to either record. Stopped while it is being played, it never reaches the result screen. Stopped by the end-of-match comparison (the other machine's final message names another winner or another final position), it shows the error panel instead of the battle and the page refuses to write it (`nm.countable()`; the scene underneath still plays its last turn and reaches its result screen, unseen: the battle canvas is hidden behind the error panel, and the scene's own record state stays `pending` there, which nothing shows). The real-Chrome page test makes that happen with a forged final message mid-match and reads the stored profile (`pokemonarena_online_page_test.mjs profile`, F22 to F24, with the honest other tab recording the same battle as the control; `profile --mutants` takes the guard out and makes `countable()` ignore a stopped match, and F23 must fail both times). That comparison normally happens while the last turn is still being shown; if the other machine's final message only arrives after the result screen is up (a link outage at that moment) the result has already been written and stays. An abort that arrives after both machines have finished is ignored: the match was finished fairly.
* **In the lobby.** A listed game, and a challenge, shows the trainer's online record (`wins-losses`, a forfeit counts as a loss) beside the name, when the team chosen is a saved one that has played online (a random, pasted or address team carries none). It is self-reported and display only.
* **Upgrading.** A profile saved by the last build (schema 3) is upgraded the first time this build loads it: the stored document is rewritten as schema 4 (one new zeroed row, `stats.byCpu.online`; every other value is kept) and the schema 3 document is kept in the profile's history. A build that only knows schema 3 opens a schema 4 profile read-only, as for any newer profile. If the write that stores the upgrade fails (a full origin, an aborted transaction) the profile is still read: `store.loadProfile` returns it upgraded in memory (`unsaved: true`, the stored document untouched, the not-saved flag set) and the next load tries the write again; a battle cannot be recorded on it until it has been upgraded.
