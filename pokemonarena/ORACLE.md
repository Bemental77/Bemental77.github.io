# The real-battle oracle (stage OR1)

`tools/pokemonarena_rom_oracle.mjs` boots **Pokemon SoulGold v1.1.1** in the site's own first-party mGBA core
(`gba/mgba/mgba_core.js` + the pinned `gba/mgba/dist/mgba_core.wasm`, md5 `13474b3883009819a5ac7304e568cb0a`; nothing is rebuilt,
downloaded or patched, and `gba/` is read-only to it), plays the REAL game into a REAL battle that runs the game's own battle code, and
exposes frames, memory, controls and audio so the arena's battle can be compared with what the game really does.

* Library + CLI: `tools/pokemonarena_rom_oracle.mjs`. Tests: `node tools/pokemonarena_rom_oracle_test.mjs` (101 passed, 0 failed, 122 s after round 2, run 2026-11-01, machine CPU 20%).
* **Nothing ROM-derived is ever written inside the repo.** The ROM is read from `$ARENA_ROM` or `gba/gbaWasm/roms/Pokemon SoulGold (v1.1.1).gba`;
  cached savestates and PNGs go to `stateDir` / `outDir` (default `<tmp>/pokemonarena-or1`, or `$ARENA_OR1_DIR`). The tests skip loudly (exit 0, counted)
  when the ROM is absent.
* The save the route starts from is the REAL one written by the game itself in `tools/pokemonarena_savegen.mjs` (cached at
  `<tmp>/pokemonarena-sv1/real_v1.sav`, regenerated by playing the new-game intro when absent): the player is in Elm's lab with the starter "Bob" (Sprigatito Lv5).
* Determinism: the cartridge RTC is pinned (`setRtc`, same pin as the savegen), there is no wall clock, the guest advances only by `runFrame()`.

| NOT verified | listed under "Not done / unverified" at the end |

## API

```js
import { openOracle, FINDINGS, FUNCS, KEY, pidFor } from './pokemonarena_rom_oracle.mjs';
const o = await openOracle({ stateDir, romPath?, savePath?, saveBytes?, rtc?, outDir? });
await o.goto('CK_ACTION_MENU');            // restore a checkpoint (cached blob, else replay the route and cache it), then run ONE idle frame
```

| Group | Calls |
|---|---|
| time / input | `runFrames(n, keys=0)`, `press(keys, hold=5, gap=20)`, `script("A@40 w60 DOWN@16 h:UP:16 A*3@10")`, `pressUntil(keys, pred, {hold,gap,maxFrames})`, `runUntil(pred, {keys,maxFrames})`, `frame` |
| frames | `screenshotRGBA()` (copy, 240*160*4), `savePng(file,{scale})`, `sheetPng(file,[rgba..],{cols,scale})`, `frameHash()`, `hpBarFill(side)` (filled pixels of the 48-px HP bar, read off the frame; `null` while the bar is hidden) |
| memory | `readU8/U16/U32/S8/S16(addr)`, `readBytes(addr,len)`, `writeU8/U16/U32(addr,v)`, `writeBytes(addr,bytes)`, `coreRead32(addr)` (the core's own bus-neutral read, the reference) |
| state | `saveStateBlob()`, `loadStateBlob(b)` (0x61000 bytes, `GBASerializedState`), `hash()` |
| battle | `battleMon(side)`, `battleText()`, `battleFuncs()`, `inBattle()`, `setBattleMon(side, fields)`, `startBattle({foe, player, trainer, base, reach})`, `openPartyMenu()`, `playTurn(slot, {delay, record, maxFrames})`, `monBytes(spec)`, `pack()` |
| audio | `captureAudio(frames, keys=0)` -> `{ rate, rates, audioFrames, samples: Float32Array (stereo interleaved at rate), int16 }` |
| checkpoints | `checkpointNames()`, `checkpointInfo(name)`, `goto(name, {rebuild})` |

Keys: `A B SELECT START RIGHT LEFT UP DOWN R L`, combinable with `+` (`'A+B'`), or a numeric mask (`KEY.A | KEY.UP`).

**Memory writes.** EWRAM/IWRAM are live pokes into the wasm heap (the heap block is found by matching the savestate and confirmed by a poke the core's own `read32`
sees; it is re-validated on 8 sampled words every access). IO/palette/VRAM/OAM writes go through the savestate (edit blob, `loadState`; the core re-derives its caches).
ROM is read-only. Measured: **a palette write had no visible effect** across all 512 entries (probably the game copies its own palette buffer every frame; not confirmed); the test proves the write mechanism with VRAM instead.

**`goto()` runs one idle frame after restoring**, because `loadState` does not redraw (the video buffer would be stale); the machine is therefore one frame after the stored blob,
for a cache hit and a fresh build alike (tested: byte-identical blobs from two independent builds, and a forced rebuild equals the cached blob).

**Restores are deterministic with respect to history** (measured: a core that ran 700 junk frames before `loadState`, one that was `reset()` first and a fresh one produced the same
400-frame video and audio chains). `hash()` differs between a restored and a continuing machine (README of `gba/mgba`: the savestate does not round-trip PSG fields), so compare frames/audio, not `hash()`, across a restore.

**`gBattleMons` layout** (found by changing ONE party field at a time through `startBattle` and diffing the struct): species `+0x00` (u16), atk/def/spe/spa/spd `+0x02..+0x0a` (u16),
moves `+0x0c` (4 x u16), IV word `+0x14` (u32; `abilityNum` is its bit 30), stat stages `+0x18` (8 x s8, 6 = neutral, index 2 = Defense: Tail Whip took it to 5), ability `+0x20` (u16),
types `+0x22/+0x23` and a third `+0x24` (`10` = none), pp `+0x25` (4 x u8), hp `+0x2a`, level `+0x2c`, friendship `+0x2d`, maxHP `+0x2e`, item `+0x30` (and a copy `+0x94`), nickname `+0x34` (12 bytes),
experience `+0x4c` (u32), personality `+0x50` (u32), **status1 `+0x54`** (u32: burn `0x10`, poison `0x08`, sleep counter `2`, paralysis `0x40` - the Gen-3 constants), OT id `+0x88`.
`status2` (`+0x58`) is ASSUMED to follow status1 and was not exercised.

**Party structs are PLAIN, not encrypted/shuffled** (0x60 bytes: the savegen `encodeMon(m, {party:true})` layout). Proof: the game built the battles shown in the tests from structs the oracle encoded with
that encoder, and the changes of single fields appear at the offsets above.

**Type numbering in this ROM** (observation off live structs, not a table read): Marill (Water/Fairy) reads types 12 and 19, Sprigatito 13/13 (Grass), and the third type byte reads 10 in every battler seen.
So Water = 12 and Grass = 13, one higher than the Gen-3 ids (11, 12); what 10 means is unknown. FA2 should confirm against the ROM's type table.

## Scenario control

`startBattle({ foe, player?, trainer?, base='CK_GRASS', reach='intro'|'action' })` (`player` may be an ARRAY: it then replaces the whole party, up to 6 mons, and `openPartyMenu()` shows the game's own party screen for it - a 5-mon party with BRN/FNT/PAR rows, red/yellow/green HP bars and the species panel was drawn and opened) goes to `base` (a free overworld state), writes the foe party (all six slots cleared first) and optionally the lead of the player's party,
sets `gBattleTypeFlags` (0 = wild, 8 = TRAINER), points `gMain.callback2` at the battle-init callback (`0x0808d581`) and zeroes `gMain.state` (+0x438; it was already 0, so not shown to be needed), and lets the game build the battle itself (31 frames to the
intro prompt). It was shown with a Pikachu "ZAP" female Lv37 60/90 vs a Charizard "Char" Lv50 150/153: the real healthboxes drew 32 px (60/90 -> 48*60/90 = 32) and 47 px (150/153), correct names, gender symbols, grass background.

`monSpec`: `species` (ROM id), `level`, `moves[4]`, `hp`, `maxHp`, `stats{atk,def,spe,spa,spd}` (HP is `maxHp`; defaults are round numbers, NOT computed from base stats), `pp[]`, `nickname` (the game prints this field as the name, so it
defaults to the species name from the pack), `item`, `abilityNum`, `status` (the party tail word), `exp`, `friendship`, `iv{}`, `ev{}`, `pid`/`tid`/`sid`, `gender`+`genderRatio`, `shinyPid`, `shinyMod`, `tera`, ...

Measured facts about it:

* **Gender** follows the classic rule (PID low byte vs the species ratio): `pidFor({gender:'F', genderRatio})` gave the female symbol for Pikachu and the default male one for Charizard (2 cases).
* **Shiny** = yellow healthbox + gold sprite. By PID: `tid ^ sid ^ pid.hi ^ pid.lo` **0..255 renders shiny, 256 and above normal** (one tid/sid/lo; NOT the Gen-3 "< 8"). The hack's own flag (`shinyMod: true`) also renders shiny.
  `pidFor` normal uses xor `0x100`. (An early default of xor 8 silently made every test mon shiny - that is how this was found.)
* **Battle background** is chosen inside `CB2_InitBattle` from the tile under the player, so `base` decides it (`CK_GRASS` = the grass background; writing candidate "terrain" bytes had no effect). Other terrains need another overworld base state.
* A battle started this way runs a real **wild** battle; `trainer: true` sets the TRAINER flag but supplies no trainer data (use the checkpoints for the trainer battle).
* `setBattleMon` changes `gBattleMons` only: the healthbox is **not** redrawn. For anything photographed use `startBattle`.

`playTurn(slot, {delay})` picks move `slot` (0..3 in the 2x2 grid) with button presses and lets the real turn play out until the action menu returns, the battle ends, or `maxFrames`.
Returns the message sequence with frame offsets and HP before/after. Example (trainer battle, Scratch): `6:"TYPE/Normal" 7:"Bob used Scratch!" 81:"The opposing Marill used Tail Whip!" 172:"Bob's ... Defense ..." (the real text contains control codes) 286:"What will Bob do?"`
(foe 19 -> 15 HP; Bob's Defense stage 6 -> 5).

The older observation still holds: idle frames at the menu change the roll (2 draws per frame), one Lv50-Tackle-into-200-HP scenario gave damages 40,41,42,43,45,46,47 over `delay` 0..13 and a critical hit (67) at delay 2; the same delay always gives the same result (tested).
the same delay always gives the same result (tested). So a roll sweep is `for delay in 0..N: loadStateBlob(b); runFrames(1); playTurn(slot,{delay})`.

### realDamage

```js
const r = await o.realDamage({ move, attacker, defender, attackerSide: 0, weather, screens | sides, crit: false, rollIndex: 0, hit: true });
// -> { damage, crit (read from the game's message), texts[], frames, timedOut, vars:{attacker,target,currentMove,mirror}, positions:{roll,crit,acc} }
```
Method (all in the real game): restore the cached wild battle at its action menu (`CK_WILD_ACTION_MENU`, cached after the first call), overwrite BOTH `gBattleMons` records (defaults: species 0, Lv100, 999 HP, types 10/10 = the neutral "???" id, no ability/item, speeds 500 vs 5; all four move slots = the move, the other side Splash), write weather and side words, press FIGHT -> move 1,
and read the first HP drop of the defender. The RNG state is rewritten before EVERY frame with a state whose draws satisfy the request. The draw positions a move uses for roll / crit / accuracy differ per move (Tackle: crit 0, roll 1; Thunderbolt: crit 2, roll 3; Hydro Pump: crit 0, roll 1, accuracy 2; Focus Blast: accuracy 0, crit 2, roll 3), so `movePositions(move)` finds them once by probes
(forcing one position at a time to roll bucket 0 / to >= 64000 and watching the damage: roll raises damage, crit multiplies it, accuracy turns a hit into a miss), caches them in the state directory (`positions_*.json`) and `realDamage` constrains exactly those positions: roll `r` = draw in `[4096 r, 4096 r + 4095]` (r = 0 is the top roll, 100%),
crit = draw >= 62806 (not crit: <= 30000), hit = draw >= 40000 (miss: <= 2000).

Measured (Windows CPU 20-50%): **a call on a cached move costs 216-223 ms** (about 160 game frames at roughly 700-1300 frames/s: restore + knob writes + 2 button presses + the hit + 24 frames of message); **the first call for a new move adds 0.4-2 s of probes** (up to 13 trials, persisted afterwards). 16 moves smoke-tested: Thunderbolt 115/97 (rolls 0 / 15), crit 172; Slash 90/76 crit 135; Fissure 999; Seismic Toss 100 (fixed damage: no roll position); Dragon Rage 40.
So 300 combos over about 60 distinct moves take about 300 x 0.22 s + 60 x 1 s = roughly 2 minutes.

Verified results with it (before/after at the same roll, defaults Tackle 52 at roll 0): the 16 roll indices give `52,51,50,50,49,49,48,48,47,47,46,46,45,45,44,44` (non-increasing, 85% at the bottom); crit x1.5 and the game prints "A critical hit!"; crit with roll 7 = 1.5 x plain roll 7;
Focus Blast (70%) with the accuracy draw forced high hits, forced low misses; rain/sun, Reflect/Light Screen/Aurora Veil, Atk +2 (x1.962), Def +2 (x0.519), burn (x0.5), paralysis/poison (x1), sleep/freeze (0), Huge Power (x1.962), Choice Band (x1.481), Life Orb (x1.308), STAB (x1.5 with a Normal-type attacker; types are the ROM's ids, Normal = 1), Levitate vs Earthquake (0 vs 115). All in `node tools/pokemonarena_rom_oracle_test.mjs --only round2`.

**Caveats (assumed):** the draw positions are probed with ONE standard scenario and assumed to be the same for other attacker/defender configurations; abilities or items that consume extra draws before the roll (Static-like triggers, King's Rock, Quick Claw ...) would shift them. A cheap guard: the 16-roll table of a combo must be non-increasing; if not, probe again with that combo's own stats via `positions:` override.
The rolls assume the roll index is `(16 v) >> 16` with 0 = 100% (FA2's statement; consistent with the monotone table and the 100% -> 85% span, not read from the ROM by me). Multi-hit moves report the FIRST hit's damage. Secondary effects use the other forced draws (mid-high values); their trigger direction is not pinned.
