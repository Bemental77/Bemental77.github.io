# Pokemon Arena

A Gen 3 style Pokemon battle game for this site, built on the data and art of the **Pokemon SoulGold v1.1.1** ROM that the GBA page already
serves. You fight a CPU opponent with random teams (Quick Battle) or with teams you build in the Team Builder, or **a friend over the internet** (`ONLINE.md`).
It runs entirely in the browser: nothing you make is uploaded, there is no server, and no third-party code or CDN is used (a friend's connection is made
with the site's own `lib/netplay.js`, the same pairing every emulator page uses).

Everything you see comes from the ROM, decoded in your browser when the page opens: the terrain, the Pokemon sprites and icons, the fonts, the
windows, the menus, the HP bars and (when sound is on) the cries. The battle messages are the ROM's own strings. The few words the ROM has no
line for (the hub's menu words, the result buttons, the start-menu rows) are written by this site and drawn in the ROM font; `scene.js` lists
the ones a run actually used. Plain DOM text appears only where a form control needs it (inputs, selects, buttons on the editor).

## Run it locally

From the repository root, in Git Bash or any shell where `npm` works:

```bash
npm run web                      # = node tools/devserver.mjs, port 8080
# then open  http://localhost:8080/pokemonarena/
```

On this Windows machine PowerShell blocks `npm.ps1`. Use any of these instead (they run the same server):

```bash
node tools/devserver.mjs         # any shell; PORT=8097 node tools/devserver.mjs picks another port
npm.cmd run web                  # PowerShell / cmd
```

Use `npm run web` / `node tools/devserver.mjs`, **not** `python -m http.server` (`npm run web:simple`): the dev server answers HTTP Range requests
and sets the headers the other emulator pages need; the Arena only needs plain file serving, but its tests run against the dev server.

The ROM is fetched from the address `lib/asset_base.js` points at (`/gamedata/gba/gbaWasm/roms/Pokemon SoulGold (v1.1.1).gba` unless the page
overrides it). It must be byte-identical to v1.1.1: the length, the header and the SHA-256 (`8071e2c3...5060a`) are checked before anything
is drawn, and a missing or different ROM stops on an error screen that says which.

## Playing

Every screen works with a mouse, a keyboard, a controller and a touch screen, each on its own, and you can switch between them at any time (the hint line under the screen
changes to the device you used last). **CONTROLS** (the hub's menu row and header button, the Team Builder's header button, or the battle's pause menu) opens the same panel dialog everywhere.

* **Mouse:** hover moves the cursor, click chooses (a click on the left half of a setting row steps it backwards), right click goes back, the wheel moves up and down. The battle's move menu shows two chips over the picture's top-right corner, **Back** and **Info**: Info (or a click on the PP / TYPE boxes beside the moves) reads the highlighted
  move's description, as the keyboard's C and the controller's X do. With no keyboard at all, clicking into a text field offers a small **Keyboard** button that opens the on-screen keyboard (it goes away as soon as a key is pressed).
* **Keyboard:** arrows or WASD move, Z or Enter = A (choose), X, Backspace or Esc = B (back), left / right change a setting, C = info, P = menu (Esc also opens the pause menu at the battle's action menu).
  On the editor and the dialogs Tab, arrows and Enter work as on any page. Keys can be rebound in CONTROLS.
* **Touch:** tap a row to choose it; an on-screen pad (D-pad, A, B, and the menu button in battle) appears under the screen at the first touch (on a phone from the start, on a laptop or desktop touch screen as soon as you touch it). Touch never needs the pad to go back:
  the move menu has the **Back** chip (every other sub-screen already shows its own way back: CANCEL on the party screen, RESUME in the pause menu, NO on a YES / NO), and a tap on the picture above the move menu,
  or beside an open pause menu or YES / NO box, goes back too. On a touch laptop or tablet that also has a mouse the pad follows the device in use: the first touch shows it, the first mouse move hides it. In the editor everything is an ordinary button, field or list.
* **Controller:** D-pad or left stick moves, A chooses, B goes back, Start opens the battle menu, the shoulder buttons switch the editor's tabs. The Xbox / Nintendo layout is chosen automatically and can be forced in CONTROLS.
  Text fields: **A on a text field opens an on-screen keyboard** (team name, nickname, search box, a pasted team code) that the d-pad drives; X deletes, Y adds a space, Start accepts, B cancels.
  On the hub's main menu B asks "Press B again to leave the Arena for the site" (a second B within 4 seconds leaves). **A controller can not be locked out by rebinding:** the Controls panel refuses a change that would leave Confirm, Back or the d-pad with no button
  (and a saved list that is empty is ignored on load), and **holding Start and Select together for 2 seconds anywhere puts the controller buttons back to the defaults**, whatever they were rebound to. The hub's and the Team Builder's "game file could not be loaded" screens
  work with a controller too (d-pad to Try again / the way back, A to press, B leaves).
* **Sound** is **on** by default, at **half the slider** (Master 50%), and **the music starts as soon as your browser allows it**: the page tries at load, and a click on the site that brought you here usually already allows it (Chrome carries that click to the next page of the site: measured, `MUSIC.md`), so a battle started from the hub plays its music at once with no second click. Where the browser refuses (a typed address, a bookmark), your very first click, tap or key press **anywhere on the page** starts it, no Sound button needed, and a hint says so until then (a controller button does not count: a browser rule). Anything you chose before (muted, another volume) is kept: the new defaults apply only when nothing is stored.
  The hub's SOUND row, the **Sound** button in the header of the hub, the battle page and the Team Builder, and the battle pause menu's SOUND row all open the same **SOUND panel**
  (volumes, mute, soundtrack, a test cry); **M** mutes and unmutes on any page. See *Sound and music* below.
* **Import from a save:** the hub's IMPORT SAVE row (or "Import from a save" in the editor) opens a screen where you choose your own SoulGold v1.1.1 `.sav` file (or drop it anywhere on the editor). It lists
  every Pokemon with its ROM icon, level, nature and whether it is legal under the destination team's rules, needs fixing (with the reasons) or could not be read (with the reason); you tick what to bring,
  choose a new team or a team with room, and Import adds them to your profile (a profile named after the save's trainer is made when you have none). The file is read in your browser, never uploaded and never changed.
* **The lead preview (6v6).** A 6v6 battle opens on a preview screen like the 3v3 team preview: your Pokemon down the left, the foe's down the right, the title the ROM's own party-menu line "Choose a Pokemon.". Pick the Pokemon you want out first (A, a click or a tap on its row) and the screen asks "Send out this one first?" with YES / NO (the ROM has no line for the question, so it is the one piece of site-written text here, listed in `scene.fallbacks()` as `confirm.lead`); the whole team is numbered in the order the battle will use (the lead 1, the rest in team order), NO or B goes back with nothing chosen, YES sends it out first. The CPU picks its own lead the way it picks for 3v3 (`ai.js`, a preview of one: it answers before you do and cannot see yours; the same seeds give the same lead). A team of two to six chooses among its own members; **a team of one has no lead to choose, so it gets no preview** (the battle starts at once). Online, both players choose, and the two leads are committed and revealed together like every other round (`ONLINE.md`). The pause menu, FORFEIT and the Controls panel work on it as on the 3v3 preview, with the keyboard, the controller, the mouse and a finger alike.
* **"Will you switch your Pokemon?" (the free switch).** Like in a Pokemon trainer battle: when the CPU's Pokemon faints and it has another, the CPU names the one it will send out next and asks, in the ROM's own words, "CPU Normal is about to send out <MON>." and, on the next page, "Will you switch your Pokemon?" with a YES / NO box (the cursor starts on YES; A or a tap on YES, B or a tap on NO or beside the box is NO). **YES opens the party screen** (CANCEL, B, a right click or a tap on CANCEL comes back to the question), and the Pokemon you pick comes in **first and for free**: it uses no move and no turn, takes its entry hazards and its entry ability, and only then does the CPU's Pokemon come in (an Intimidate finds nobody: the foe's Pokemon has fainted and its replacement is not out yet, as in the game). **NO** changes nothing. It is asked only if you have another living Pokemon and your own Pokemon is able to leave (not trapped) and has not fainted too; **only against the CPU: a battle against a person has no such question**, and neither does a battle with a team of one. The CPU's replacement is chosen before you are asked and is the same whatever you answer. **BATTLE STYLE** is the hack's own Options row ("Battle Style": **Shift**, the default, asks; **Set** never asks; the words are read from the ROM, which also says "Shift offers a free switch when an opposing Pokemon faints. Set sends the next foe in without a free switch."): the pause menu has a **BATTLE STYLE: SHIFT / SET** row that flips it at once, in the middle of a battle too (a battle on SET is, frame for frame, the battle that was played before the question existed: the engine still offers and the scene answers NO for you, and the log holds that NO), `localStorage['arena.battlestyle']` (`switch` or `set`) remembers it, and `?style=switch|set` in the battle address overrides it for that visit without storing it (any other value is an error screen that does not echo it). Your answer is an ordinary recorded choice, so a reload in the middle of a battle replays it (a reload AT the question comes back to the question); the match recap and the record count a free switch as a switch and never as a turn (`ENGINE.md` `freeSwitch`). The Tower and any other caller get it by passing `freeSwitch: true` to `createMatchController` and the page's `style` setting to the scene.
* **Animations** are on by default: a move plays its own animation from the ROM (the sprites, backgrounds, flashes and sound cues of the game's battle-animation code, run by `js/move_anim.js`; `ANIM.md` says which moves are exact, approximate or missing), the scene also asks that engine for the status-condition, stat-change, weather and recall animations (they play wherever it has them), and for the battle's own scenes (`animator.start('system', id)`: the opening with the foe trainer sliding in and both Pokemon sent out, every send-out and recall, every faint and every hit blink are the ROM's battle code, motion, cries, the shiny sparkle and sounds included; the scene types its own messages over them). Without the engine (or with animations off) a Pokemon comes out of a ball drawn by the scene and the foe's front picture swaps at the times the ROM gives. The pause menu has ANIMATION ON / OFF and BATTLE SPEED 1X / 2X / 4X; `?anim=0|1` and `?speed=1|2|4` set them for one visit (`?speed=slow|mid|fast` is still the text speed). Both are remembered in this browser (`arena.anim`). A button press does not skip an animation (the game does not either); `?animskip=1` makes a press skip it.
* **Levels:** the default ruleset (Standard) battles every Pokemon at Lv 50 whatever level it has in the editor. The editor says so beside the level ("Battles run at level 50") and on each team slot ("Lv 100 (fights at Lv 50)");
  a Pokemon's own level only decides which level-up moves it may know.
* **The result screen** takes no choice for its first 90 frames (about 1.5 s), so mashing A, clicking or tapping through the end of a battle cannot start a REMATCH (or open the recap) by accident; after that A, a click or a tap chooses the button under the cursor. The cursor starts on REMATCH and runs round the four buttons RECAP, REMATCH, EDIT TEAM / NEW BATTLE, BACK TO HUB (left / up = previous, right / down = next). **A on RECAP opens the match recap**; its last page goes back to the result screen with the cursor still on RECAP, so holding A down loops through the recap and can never reach REMATCH.
* **The match recap** has seven pages (see *Stats* below): left / right (or up / down, L / R, the wheel) turn the page, A turns it and, on the last page, goes back, B and Start go back at once; a mouse or a finger uses the PREV / BACK / NEXT buttons under the page, a click or tap on the page itself is A, a right click is B. It plays the same menu sounds as the other menus.
* **Reloading in the middle of a battle resumes it.** The battle page keeps the choices you made in this tab's `sessionStorage` (nowhere else, never sent anywhere) and, on a reload or a Back / Forward step, replays them into the same seeded
  battle, proves the result is the same state (same hash, same turn), plays the history at speed and silently, and shows the action menu of the turn you were on. A visit that is not a reload (typing the address, following a link), a replay that
  does not come out identical, or a browser with `sessionStorage` blocked starts at the team preview as before. In a 6v6 battle the lead you chose is the first choice of the saved history, so the same Pokemon is in front after the reload; **a record saved by the build before the lead preview existed** (its first choice is a move, which the new battle refuses at the preview) is refused cleanly and the battle starts again at the lead preview. Finishing a battle, choosing a result button or leaving through BACK TO HUB forgets it.
* **Error screens are plain.** When the game file cannot be loaded or is not SoulGold v1.1.1 the hub, the battle page and the Team Builder show the same words and the same buttons (Try again only when trying again can help); the file's address and the server's
  status are for a developer and go to the console and to the hover text of the explanation, not to the screen.

The details of the input layer are in `INPUT.md`.

## Sound and music

The music, the sound effects and the cries are the ROM's own, decoded and played in your browser (nothing is downloaded but the ROMs this site already serves, and no audio file is stored anywhere).
`js/music.js` plays the songs of the SoulGold ROM's m4a (MP2K) sound engine (what is exact and what is approximate in it: `MUSIC.md`); `js/music_map.js` says which song plays where, and
`MUSIC_MAP.md` gives the evidence and a confidence for every pick (several are mood choices marked *low*; they live in that one file and are easy to change). A second soundtrack, **Ultra Violet**
(the other GBA hack the site serves), plays through the same engine; its ROM is fetched only when you choose it in the SOUND panel (progress and a clear error if it cannot be loaded; a remembered
choice that cannot be loaded plays SoulGold for that visit and keeps your choice).

**When you hear what.** The hub plays `hub`, the Team Builder `editor`, a battle, **from the very first frame (the team preview included)**, `battle_easy` / `battle_normal` / `battle_hard` by the CPU level you chose (the wild, trainer and leader themes: the classic battle start; `MUSIC.md` "What plays when a battle begins"), and the result
screen the win fanfare (`victory_sting`, the ROM's short badge fanfare) and then `result_win`, or the lose fanfare (`defeat`) and then `result_lose`; a draw goes straight to `result_lose`. A fanfare hands over to the
next song when it ends; the ROM's `victory` songs *loop*, so one is never waited on (a soundtrack with no sting plays its looping victory song as the result music). When a soundtrack has no song for a key,
`music_map.js` walks its fallback chain, and then the page stays silent. The battle pause menu keeps the music playing at half level; the SOUND panel plays it at full level so the sliders can be judged. Each page
starts its own song when it opens: a page change is a new page, the song restarts, and nothing pretends otherwise (and a page that is closed cannot fade, it stops).

**The SOUND panel** (the same dialog on every page): *Master*, *Music* and *Effects and cries* sliders in 5% steps, **MUTE**, the **SOUNDTRACK** choice and **Play a test cry** (a cry through the effects bus; it also plays
when you let go of the Effects slider, so you can hear the level). Mouse: click or drag a slider, the wheel over a slider is 5% per notch, hold the **-** / **+** buttons to repeat (after 0.4 s, then every 0.09 s).
Touch: the same, every target is at least 44 px, and a finger that lands on a slider and drags up or down scrolls the panel without moving the slider (a tap, or a sideways drag, sets it). Keyboard: Tab, then Left / Right (5%), Home / End on a slider; Enter or Space on a button; **Esc closes in one press**. Controller: the d-pad moves between controls,
**A on a slider starts adjusting it** (Left / Right 5%, Up / Down 10%, a held direction repeats), **B finishes**, B again closes. A closed panel returns the focus to where you were, and the battle's pause menu comes back on its SOUND row.

**The audio bar and the menu-music changer** (`js/audiobar.js` + `audiobar.css`, one module and one stylesheet for the hub, the battle page and the Team Builder, so it is the same everywhere by construction). A **volume slider** is always on screen in
the page header: a mute button, a slider in 5% steps and the percentage (a keyboard arrow is one step; a tap or a drag sets it; a finger that scrolls the page does not move it). It drives the page's one mixer, so it is **the same setting as the SOUND panel's Master slider**:
move either and the other follows, a reload keeps it, and the **M** key and another tab are followed too. Dragging it up while muted unmutes (a click, tap or key on the bar is a user activation like any other, so it can also be what starts the sound).
On the two menu pages (hub, Team Builder) a **music button** opens a short list: **Automatic** (the game's own song for each menu), every song the soundtrack in use can play on a menu, and **Off** (no MUSIC on the menus: the hub's cursor / select / back sounds still play, after a reload too; the Team Builder plays no sound effect, so with Off it loads no music engine at all, and no Ultra Violet ROM either); previous / next buttons and the arrow keys step through it. The songs offered are the
ROM songs `music_map.js` says **loop** and are background music, each once (the hub and the Poke Center are the same ROM song, so it is listed once), named for the player ("Pokemon Center", "Battle: wild Pokemon", "Victory: gym leader": a table in `menu_music.js`, not music_map.js's developer notes, which are not shown); a song the soundtrack lacks (Ultra Violet has no rival
battle theme) is not offered while it is in use, and a stored pick for one plays the screen's own song and is kept for when the first soundtrack comes back (the bar then reads "Automatic (Battle: rival is not on this soundtrack)" and Automatic is the entry that is checked). The pick is `{"v":1,"pick":"auto"|"off"|<music_map key>}` in `localStorage['arena.menumusic']` (a damaged value is repaired to Automatic)
and applies to **every menu page**. **The battle page has no changer: it keeps choosing its music by the battle** (team preview, the CPU level's battle song, the result), whatever the menu pick is. **The open list is a modal dialog:** the arrows, W A S D (the keys your bindings give the d-pad: rebind Up and the new key moves, W stops) and Home and End pick songs, Tab stays inside, Esc closes it, and no other key (Z, X, Backspace, PageUp / PageDown) and no controller press reaches the menu behind it. A controller drives the open list too: the d-pad moves through it, A picks the focused song, B closes it and gives the focus back to the music button (on the Team Builder that is the page's own navigation layer; the hub, which ignores the pad while a dialog is up, gives the list a layer of its own). **Focus:** after a mouse or touch use of the bar (Mute, the slider, closing the list with a click) the focus goes back to the page's picture (the hub's and the battle page's canvas; the Team Builder has none, so the control is just released), so the arrow keys and Enter act on the game again instead of on the slider or the button; keyboard use keeps its place (Esc returns to the music button). **Layout:** wide screens carry the bar inline in the header; a portrait phone gives it a row of its own under
the header (the battle page keeps it in its header's first row, which has the room; the hub takes back the margins of its "Play online" row so a 568 px phone still shows the whole touch pad); a phone held sideways in **fullscreen** has no header, so the bar floats beside the exit-fullscreen button folded
to one speaker button that opens it with a tap. It is hidden while a page is loading or has failed. **Not covered:** a controller cannot reach the bar on the hub or the battle page (it cannot reach their header buttons either: those pages are driven through the canvas); on the Team Builder, whose navigation layer covers the whole page, the bar's controls
are ordinary focusable controls the layer reaches (the editor page test drives Mute, the slider and Menu music with the d-pad; A on Menu music opens the list, the d-pad cannot leave it, B closes it). The controller route to the same volume is the hub's SOUND row, which opens the SOUND panel; on the hub a controller cannot OPEN the music changer (open it with the mouse, a tap or the keyboard; the pad then drives the open list, see above). The sound-start hint treats the bar as part of the header (it never lands on it), including while it floats.

**How it works.** `js/audio_mixer.js` owns the page's only `AudioContext`, created at load by the page's early try (`earlyStart`: the browser runs it or keeps it suspended) or, failing that, at your first click, tap or key anywhere (even when muted, so a controller can unmute later); a visitor who stored a mute gets no context at load. Three buses: *master*
(to the speakers), *music* and *fx* (cries and effects), each a gain that moves in a 30 ms ramp (no clicks). **The UNITY sliders (70 / 60 / 80%, `UNITY` in `audio_mixer.js`) are the positions where every bus has gain 1.0, and gain 1.0 is the
level the real game plays at** (a new visitor deliberately starts lower: Master 50%, gain 0.51, about 6 dB under the game, with Music and Effects at their unity positions; the gain law is anchored on UNITY, so moving the starting volume moved nothing else): the engine's output is calibrated to the real game in the mGBA oracle (MUSIC.md), the site's own volume slider for the GBA page also defaults to gain 1.0 (`lib/volume.js`), and the sink was measured
against the real game's level for the same song: -0.02 dB in a real browser, within 0.1 dB on six SoulGold songs offline, within 1.3 dB on the two Ultra Violet songs (`tools/pokemonarena_sound_level_test.mjs`,
`tools/pokemonarena_sound_real_test.mjs`). Below a bus's default position the gain follows a **square law** ((position / default)^2: half the default is -12 dB, loudness is judged roughly logarithmically); above it the gain
climbs in a straight line to **+3 dB** at 100% per bus, so master and music together reach +6 dB over the game. (Before round 4 the same defaults gave 0.7^2 x 0.6^2 = 0.176, 15 dB under the game: that is why the music
was nearly inaudible. Saved positions are kept as they are, so an old save at 70 / 60 / 80% now plays at the game's level, and one at 100% is +6 dB louder than it was.) A **soft limiter** (a WaveShaper between the master
bus and the speakers: the identity up to 0.8, saturating smoothly toward 0.95) keeps a loud song, cries and effects together from clipping even with every slider at 100%: measured in a real battle at 100 / 100 / 100% the
signal reaches 1.8-2.0 before the limiter and 0.93 after it; without it the same battle reached 1.4-1.6 at the speakers (clipping). Mute ramps the master to exactly 0 and then **suspends** the context, so a muted or hidden tab costs no CPU. Settings are the JSON
`{"v":1,"master":0.5,"music":0.6,"fx":0.8,"muted":false,"soundtrack":"soulgold"}` in `localStorage['arena.audio']` (these are the defaults for a visitor with nothing stored; every earlier build wrote 0.7 / 0.6 / 0.8, and those stored values are kept as they are: the schema is unchanged, `v` is still 1); a damaged value is repaired field by field, and the old `arena.sound`
(`1` / `0`) is read once when `arena.audio` does not exist yet. `js/music_director.js` turns "which screen" into a song and keeps it in step with the mixer; `js/sound_panel.js` is the panel; `js/sound_system.js`
is the one object a page creates. The music engine and the song map are imported after the page is up and the game never waits for them: until the first song is ready it is playable and silent.

**Browser rules you may run into.** A page may start sound only where the browser's autoplay policy allows it (the site's permission, or a click on the previous page of the site: the page tries at load) and otherwise only after a click, tap or key press (a bare Shift key is not one in Chrome), and a gamepad button is not one of those (the page tries it anyway): with only a controller the page shows "Click, tap or press a keyboard key to start the sound (a controller button cannot). Esc or a controller button hides this."
and stays silent until one of them happens (a controller can still set every level in the panel meanwhile). The hint sits under the picture or at the bottom of the window, never over a control and never in the header
bar; it is text only (it ignores the pointer, so it cannot swallow a click or a tap), a click, tap or key press starts the sound and removes it, and **Esc or any controller button hides it without starting any sound**

## Stats: the match recap and the battle record

Two features share one collector. `js/match_stats.js` folds the battle engine's **event log** (the same events the scene plays, `battle.events`) into a deterministic summary of the match: the same log gives the same summary byte for byte, whether the battle was played live or rebuilt by replaying the saved choices after a reload. Nothing is estimated from the screen.

**What a match summary holds** (per side, per Pokemon and per match): damage dealt and taken (HP and percent of max HP), KOs scored, times fainted, the moves used (with counts), hits landed, critical hits, super effective / not very effective hits, moves that had no effect, misses, status inflicted and suffered, HP healed, switches, turns on the field, the HP left at the end; for the match its turns, the first blood, the biggest single hit (who, which move, how many HP, what percent of the target), the last hit, the closest call (the lowest HP a Pokemon that never fainted reached), the longest KO streak, the turns of each weather and terrain, and the flags *no faints*, *one-Pokemon sweep* and *comeback* (won after being two Pokemon down). Damage that no attacker caused (entry hazards, Leech Seed, a binding move, Rocky Helmet ...) is "foe" damage, damage from a Pokemon's own move / item / ability (recoil, Life Orb, a confusion hit, Explosion ...) is "self" damage, and status damage and weather are "environment" damage: only an attack is credited to a Pokemon (as dealt damage and as a KO), the rest counts as damage taken. Identities that the tests check on 240 real battles: damage taken = hit by attacks + foe + self + environment; the attacks one side dealt are exactly what the other took from attacks; faints = the other side's KOs + own-goal faints + environment faints. **MVP** (a documented score, nothing hidden): 100 points per KO scored plus the damage dealt as a percent of the victims' max HP; ties go to the Pokemon that fainted less, then the lower team slot.

**The recap** (the RECAP button of the result screen) shows it on seven pages drawn from the ROM's windows, fonts and colours: SUMMARY (the result, the turns, the MVP with its picture, the biggest hit, the closest call, the first blood or the record this battle set), MOMENTS, YOUR TEAM and FOE TEAM (dealt / taken / KOs / HP left, per Pokemon), MOVES (the most used moves of both sides), COMPARE (hits, crits, effectiveness, misses, status, healing, switches side by side) and RECORD (what was written to your profile, the records this battle beat). A forfeit, a draw and a quick battle with no profile each have their own words. Every cell of every page was measured against the ROM font widths on 100 real battles plus the longest names the roster has: nothing is cut or overlaps (`tools/pokemonarena_recap_test.mjs`).

**The record on the profile.** (A battle against a person is kept the same way, from schema 4 on: its own ONLINE row and the opponent's name; `ONLINE.md` has the details.) A finished battle is written into the profile when its result screen appears: the profile that owns the team in the address (the lookup EDIT TEAM uses), else the profile that is *active* in this browser (the one the Team Builder or the last team battle chose); with **no profile** nothing is written and the recap says so. One write is one IndexedDB transaction that reads the profile, folds the match in and saves it, so two tabs finishing battles at the same moment lose neither (`store.recordMatch`; `tools/pokemonarena_career_test.mjs` runs 24 concurrent writes through two connections, and the page test runs 20 through real IndexedDB). It is **idempotent** by a match id (seed, format, CPU level and the time the page started): the same id twice changes nothing, a reload starts a new battle (a new play, a new id), a reload in the middle of a battle replays the saved choices silently and the battle is counted once, when it ends. **Leaving a battle in the middle** (BACK TO HUB from the pause menu, closing the page) records nothing (against a person too: the player who leaves records nothing for themselves, and the one who stayed records the win; `ONLINE.md` has the details); **FORFEIT** is recorded as a forfeit (not a loss); a draw at the turn cap or with both sides out is a draw. REMATCH and BACK TO HUB wait (at most 1.5 s) for a write that is still under way. A write makes no history entry (the editor's ring of 5 recoverable revisions is not used up by battles); restoring an old revision of the teams keeps the current record.

**What `profile.stats` holds (schema 4).** Counters: `wins losses draws forfeits` (a forfeit is its own outcome), `streak` (the current run of wins) and `best`, `lastMatchAt`, `firstMatchAt`, `playMs` (the battles' own clock: frames played / 59.7275 Hz), `byRuleset` (`{w, l}`: a forfeit counts as an l, a draw as neither), `byFormat` (3v3 / 6v6) and `byCpu` (easy / normal / hard / **online**: a battle against a person, schema 4), each `{w, l, dr, f}`; `totals` (turns, KOs, faints, damage dealt and taken, hits, crits, super effective, resisted, no effect, misses, status inflicted, HP healed, switches); `bests` (the biggest hit ever: species, move, HP, percent, target; the fastest win and the longest battle in turns; the best KO streak); `fav` (how often each species was used, each move was used and each species was the MVP: at most 24 / 24 / 12 entries, the least used makes room for a new one and the newcomer takes over its count + 1, so a kept count is never below the truth); `recent` (the last 20 battles, newest first: id, date, format, CPU, result, turns, the MVP's species, the species of the team). Every counter is a non-negative integer that saturates at the largest safe integer; every map and list is bounded, so a profile stays small. The schema version went from 2 to 3: **opening a version-2 profile migrates it** (every old counter stays, the new keys start at zero; the old revision stays in history), and a profile written by a *newer* build opens read-only, as before. Hostile or damaged values are repaired key by key and what cannot be repaired is kept in the unknown-field bag, never silently dropped.

**Export and import.** The record is part of the profile, so a profile export carries it (the checksum covers it). What an import does with it: *as a new profile* copies the file's record; *merge into the active one* leaves the active profile's record exactly as it is (the file's record is NOT added, so merging the same file twice cannot count its battles twice); *replace the active one* takes the file's record (the replaced profile is backed up first). The import preview says which of the three will happen, with the file's battle count. Team codes do not change.

**The RECORD screen** (the hub's third row) shows the record of one trainer in pages: OVERALL (battles, win rate, won / lost / drawn / gave up, win streak, first and last battle, time played), MODES (3v3, 6v6, each CPU level, and ONLINE once the trainer has fought a person), FAVOURITES (most used Pokemon and moves, most MVP awards), HIGHS (biggest hit, fastest win, longest battle, best KO streak and win streak), TOTALS, RECENT (the last 20 battles, five to a page) and RESET. With several profiles the trainer is switched on the first line (up / down puts the cursor there, left / right or a click on the name switches; with one profile up / down turn the page). **RESET RECORD** is on the last page, behind a YES / NO that starts on NO; YES empties that trainer's record only (teams and Pokemon are not touched), takes an automatic backup of the old record first and keeps a history entry. A profile made by a newer build shows a read-only notice instead. With no profile it says so and A opens the Team Builder.

**What is not recorded:** battles left in the middle, per-move accuracy, anything about the foe's team beyond its result, and anything without a profile (a Quick Battle with no profile still has its recap, but nothing is kept). The record is yours alone: it is stored in this browser, nothing is uploaded, and clearing the site's data erases it (Export in the Team Builder keeps a copy).

## What is approximate

True as of this build; each item is also visible in the code it names.

* **The battle engine is first-party, not the game's code.** It reads the ROM's data tables and follows modern (Gen 5+) rules where the ROM does not say; `ENGINE.md` lists every
  mechanic and marks the ones that are *assumed*, not decoded. It supports 688 of the ROM's 936 moves, 173 of its 523 abilities and 662 of its 930 items (counted from `engineSupports(pack)`):
  a team that uses anything else is **illegal** and is refused with the reason from `rules.js`. Singles only; a battle ends in a draw at turn 300.
* **Animations are the ROM's, but not all are verified or present.** A move animates through `js/move_anim.js` (per-move status in `ANIM.md`); a move it has none for, or animations switched off, falls back to the old lunge + blink (`__arenaBattle.animInfo()` lists what a battle asked for and what the engine answered). The status-condition, stat-change, weather and recall animations are asked for too and play wherever that engine has them. Measured with `node tools/pokemonarena_anim_census.mjs` on this build: of the 935 moves 635 are exact, 298 approximate and 2 fallback (moves 502 and 852, which use the lunge); of the 22 general, 9 status and 7 special animations the scene asks for, 36 are exact and 2 fallback (the Poke Block throw and the Safari ball, which no battle here uses). All 1094 animations the engine knows: 786 exact, 304 approximate, 4 fallback (`ANIM.md`). "Exact" means the ROM's own code ran with no known source of divergence; `ANIM.md` says how many were compared frame for frame with the real game. The battle's own scenes (opening, send-out, recall, faint, hit) are the ROM's code too when the engine answers `exact` or `approx` for them (`js/anim_sys.js`; the arena plays the TRAINER opening, id 1, because the opponent is a CPU trainer; the foe trainer picture is a ROM trainer picked by the CPU level from the ROM's own trainer table: easy = Youngster / Lass / Bug Catcher / School Kid / Camper / Picnicker, normal = Cooltrainer / Gym Leader, hard = Elite Four / Champion, one per battle; the player's back sprite is the ROM's male one, because the arena stores no gender for the player). Their hidden pre-roll (100-250 ms of ROM code) is run in 3 ms slices by `animator.prepare()`, one slice a tick, while the previous picture plays: the next two events of the queue are prepared ahead, the opening's battle state is pre-rolled while the opening plays, and the engine shares a pre-roll between events that start from the same parties; a step whose pre-roll is not finished holds the previous picture and the scene keeps ticking. Measured in headless Chrome (`ARENA_BROWSER=1 node tools/pokemonarena_anim_scene_test.mjs`, a 3v3 battle of 10,174 frames with 28 system runs): no frame outside a ROM move animation went over the 16.74 ms frame budget (plus 1 ms of noise), the worst frame of the whole battle (tick + render, inside a heavy move animation) took 18.8 ms, and the previous picture was held for a pre-roll on 2.5% of the ticks (256 of 10,174) (round 3: 22 stalls of 94-151 ms, worst tick 150-310 ms); see `ANIM.md` Round 4. The first intro of a visit is warmed behind the boot screen. Where the engine has no system animation (or animations are off), the scene's own versions play, and there the ROM's per-species motion routines are not run (a Pokemon does not move on send-out or when sent back; only its two front pictures swap, on the ROM's own delay and durations), the ball's throw arc and release timings are chosen by eye (the ball art and palette are the ROM's), and there is no shiny sparkle. Not done in either: the low-HP healthbox bounce, the HP and EXP bar animations of the ROM's own battle scripts. Without an animation, timings were chosen by eye, not read from the ROM (`scene.js` header).
* **Screens composed from ROM pieces, not copied from the game:** the party, team-preview and result screens, and the hub. The game's own party-menu background and panel art were not located.
  Some battle-screen coordinates, the HP-bar colour thresholds and the text speeds are recollection of the Gen 3 decompilation, not found in this ROM (`battle_ui.js` header).
* **Ability lines (round 6).** The engine can put 155 different `fx` codes on an `ability` event; `tools/pokemonarena_scene_events_test.mjs` has a table with one row per code that says what the player sees: **a ROM line** of its own (Neutralizing Gas, the four Ruin abilities, Unnerve and As One, Slow Start, Supersweet Syrup, Harvest, Disguise, Liquid Ooze, Sturdy, Magic Bounce, Mummy, Wandering Spirit, Wind Power, Anger Point, Dancer, the weather abilities, Cursed Body), **the next event's line** (a stat change, a status, an immunity, a field ...), or **only the HP bar / nothing** (Lifesteal, Mending, Rejuvenation, Polarity Shift, Wishmaker ... : no ROM line names the ability, proved by searching the ROM text table for its name). Round 7 closed the first "not done": Static, Flame Body, Poison Point, Effect Spore, Cute Charm and Flash Fire's first absorption now show the ROM's own line (the next absorption the plain immunity), Rapid Spin / Mortal Spin name each hazard they blew away in the game's order, Defog and Tidy Up name each one they cleared, Snatch, Skill Swap, Role Play and the other `copy` events have their lines, Stockpile says "stockpiled N!", joins Defense and Sp. Def into one line and says the stockpile wore off. It's super effective!"), and what Rapid Spin frees its user from, in the game's order: Speed rose, "got free of <foe>'s <move>!", "shed Leech Seed!", then the hazards. The binding moves now name themselves everywhere (each of the ten has its own start line, "is hurt by <move>!", "was freed from <move>!"); before, every one read "became trapped in the vortex ... hurt by the trap".
* **Some text is not the ROM's:** a handful of battle lines (for example Life Orb recoil, a drawn game at the turn cap), the result-screen buttons, the start-menu rows and everything on the hub's menu (`scene.js` header).
* **Cries:** decoded from the ROM; the normal cry plays at the wave's own rate. The faint cry's pitch is the nominal reading of the game's pitch law and may be a fraction of a semitone off,
  and that the game's faint cry is that mode was inferred, not traced (`cries.js` header).
* **Sound and music (the page side; the engine's own list is in `MUSIC.md`):** **nobody has listened to it in this build**: the engine's own checks are listed in `MUSIC.md`, and the page side is checked by tests that record every
  call made to a stand-in `AudioContext`, not by ear. Which screen plays which song is a design choice backed by `MUSIC_MAP.md`; the hub, editor, preview, defeat and result songs are low or medium confidence mood picks.
  The menu sounds are played when the cursor or the screen *changed* after a key or click (a heuristic, not the game's own call sites); the send-out ball sound is attached to the scene's event
  (whether the game plays it at the same moment was not traced). **The effectiveness sound of a hit (SE 12 / 13 / 14) is played at the start of the HP drain, as the game does** (oracle: the game starts it as a separate
  sound after the move's own, and the animator never delivers it, so the hook always plays it); a faint plays SE 16 once (the animator's own copy of it is dropped, not doubled). The music pauses and resumes with the tab
  and with mute; it does not continue across a page change. The volume law (unity at the default, a square law below, +3 dB per bus at the top) and the soft limiter are choices, not the console's.
* **The low-HP warning, the error buzz and the sounds that are NOT played (round 4).** *Low HP (SE 90, Ultra Violet 83):* while the **player's** active Pokemon is in the game's red zone (alive, max HP above 1, HP at or below
  max HP / 5, integer division; the same rule as the HP bar's red) the beep starts **once**, one frame after the HP bar has stopped moving, is not repeated while the Pokemon stays red, and stops when it is healed, faints,
  is replaced or the battle ends (the game's `HandleLowHpMusicChanges` @0x08080130, run against this rule over 146 HP / max HP pairs in real turns: all agree; `tools/pokemonarena_sound_oracle_test.mjs`). In SoulGold it is one
  2.4 s pattern that ends by itself (clock 146 ticks, not looped); in Ultra Violet it is a looping song that the stop ends. *Error buzz (SE 32):* played when the hub refuses START on an illegal team. **The battle
  screen does not buzz**: the oracle shows the real battle UI plays only the select sound for a move with no PP, "already in battle", a fainted Pokemon and the give-up prompt, so neither does the arena (the 82 ROM sites of
  SE 32 are menu, party-menu, bag and PC code; no menu refusal was run in the oracle, so the hub's buzz rests on those sites and on the game's menu convention, not on a run). *Not played:* **flee (SE 17)**: the game plays
  it only when a wild battle is escaped (oracle: "You got away safely!"); the trainer-battle RUN is the give-up prompt (the arena's forfeit) and, answered YES, plays no SE 17. **EXP (SE 33 / 91)**: the arena has no
  experience. **Success (SE 31)**: its 7 ROM sites are all outside battle code and the arena has no matching event. All five ids do sound through the game's own `m4aSongNumStart` and the arena's engine renders them at the
  same length (+-0.3 s).
* **CPU levels:** EASY picks a random legal move; NORMAL picks by expected damage with some tactics; HARD adds a one-turn lookahead (`ai.js` header). The CPU never reads hidden information.
* **A team is levelled to 50 for battle** under the default ruleset (Standard: Lv 50, 510 EV); the editor shows the Pokemon's own level and says so next to it (see Levels above). Other rulesets differ: Champions fixes Lv 50, Level 5 battles at 5.
* **EDIT TEAM** finds the saved team by comparing team codes, so it opens that team only if it has not been edited since the battle began; otherwise it opens the Team Builder's profile list.
* **Picture size and Fullscreen** (`js/screenfit.js`, shared by the hub and the battle page): the 240x160 screen fills the room it is given, at its own 3:2 shape. It is snapped to a whole number of device pixels per source pixel only when that costs under 6 % of the size (a pixel-art picture is sharpest at a whole scale); otherwise it takes the whole room and is drawn with nearest-neighbour sampling (`image-rendering: pixelated`), the way the site's other game pages draw theirs, so between whole scales a source pixel is at most one device pixel wider than its neighbour. This replaced a rule that only ever rounded DOWN to a whole scale: it gave a 390 px phone at 3x density a 324 px picture and a 360 px phone at 2x one of 244 px, with half the screen empty. Now a phone held upright shows the picture edge to edge (no gutters, no frame) with the touch pad in the middle of the room under it: not at the very bottom edge, where a phone's swipe-up gesture lives and the browser's "exit full screen" toast lands (a real phone showed both on top of the buttons). A **Fullscreen** button (a corner-bracket icon in the header) uses the browser's Fullscreen API on the whole document where there is one and otherwise (iPhone Safari has no `requestFullscreen`) switches to a full layout of the page itself; on a phone held sideways that layout drops the header and gives the picture the whole height, with a floating Exit button above the d-pad. A page load while fullscreen (a rematch is one) comes back in the full layout at once and asks the browser for real fullscreen again at the first tap or key (the browser only allows that from a gesture). What is NOT claimed: no real iPhone, Android phone, Safari or Firefox was used; the no-API path was tested by removing the API from headless Chrome.
* **Coming back to the hub is not a loading screen** (`js/romcache.js`, `js/romfetch.js`, `js/boot.js`, `arena.css`; test `tools/pokemonarena_hub_return_test.mjs`). Every Arena page loads the 32 MiB SoulGold image the site already serves, so "back to the hub" used to be a loading panel, a 32 MB download (or a lucky HTTP-cache hit: a browser may not keep an entry that large), a SHA-256 of all of it and the decode. Now: (1) **a verified copy is kept in the browser's own Cache Storage**, under a key that contains the pinned SHA-256 (`arena-rom-v1`; the same copy serves the hub, the battle page and the team editor). It is written only after a download has passed the full check (length, cartridge header, SHA-256 against the pin); it is read back only if its headers name the current pin, length and revision, its body is exactly the pinned length and its header still identifies as SoulGold v1.1.1. Anything else deletes it and means "download": a missing, blocked, full or private-mode Cache Storage is a cache miss, never an error. Storing a copy also removes every other revision of the cache and any copy of a previously pinned ROM (the pin is in the key, so a new pin without a revision bump would otherwise leave 32 MB beside the new copy). Nothing from the ROM is committed anywhere; this is the visitor's own browser storage, as the HTTP cache would be. (2) **The hub's first frame does not wait for the re-hash.** A recalled copy is trusted for the first frame and its SHA-256 is re-checked right after it has been painted (handing 32 MB to WebCrypto copies the buffer on the calling thread: ~25 ms at full speed, ~90 ms on a 4x slower CPU); a mismatch drops the copy and reloads the page once through the full path, which ends at the real error screen when the ROM on the server is the bad one (the guard is `sessionStorage` `arena.rom.retry`). A recalled copy that is damaged INSIDE a table the menu decodes (right length, good cartridge header, so the cheap checks pass) cannot even build the menu: `start()` then hashes it on the spot and takes the same way out (drop, one reload under the same guard; with the guard already spent in the tab, the named error screen, and the copy is gone so the next load works). It used to be an error screen with no way out, because the re-check that drops a bad copy was only scheduled after the menu was built. A ROM that was just DOWNLOADED is always verified before the page uses it. (3) **The ROM starts loading before the page's modules have finished loading** (it used to wait for them). (4) **The loading panel is revealed 400 ms after the page starts**, so a fast return never shows it, while a first visit still gets its panel and filling progress bar. Two reveals, because either alone failed someone: a 0 s CSS keyframe (it also works if the script never starts), and a tiny inline timer in `index.html` that sets `data-slow` on `<body>` (`prefers-reduced-motion: reduce` switches every CSS animation off, and a visitor with Reduce Motion on, which iOS, Android and Windows all map to that query, would otherwise have seen an empty page for the whole 32 MB first download; the timer is inline, not in `boot.js`, so it does not wait for the module graph either, which on a first visit over a bad connection arrives late; with Reduce Motion on and no script at all nothing reveals it). While the panel is hidden it is out of the accessibility tree, so as it appears the persistent `#live` region says that the game file is loading (`boot.js` takes the message back when the panel goes). Try again after an error shows the panel at once. A return that is up inside the 400 ms never shows the panel and never writes that message: the inline timer does nothing to a page that is no longer loading (case R3c holds that deterministically, with the page state forced), and the real returns (W4, W4b, R2, R2d) are each judged against their own first-hub time, because a return that load slows past 400 ms is rightly shown the panel, for as long as it ran past the reveal and no longer; none may leave the message in the live region once the hub is up.
  Measured on this machine, headless Chrome, a repeat visit with the page's files and the ROM available locally (milliseconds from the start of the page; CPU throttling is Chrome's `Emulation.setCPUThrottlingRate`, a rough stand-in for a phone): **before**, 1x CPU: loading panel on screen for ~105 ms (ROM read 36 ms, SHA-256 25 ms, decode 36 ms), hub at ~148 ms; 4x CPU: panel for ~354 ms (ROM 109 ms, SHA-256 96 ms, decode 119 ms), hub at ~492 ms; with the dev server's `no-store` (the full download every time) the panel was up for ~313 ms. **After**, 1x: no panel, the hub is the first thing painted, at ~113 ms; 4x: hub at ~430 ms, the panel (revealed at 400 ms) on screen for under 30 ms; `no-store` server, 1x: hub at ~163 ms and no panel. On a real network the saving is the whole download, which these numbers do not include. The browser's **back/forward cache** already restores the hub itself (nothing loads at all) on browser Back when the server allows caching: the dev server's `no-store` hides that, a caching proxy shows it, and the live site's static host does not send `no-store`.
  **NOT done, and why:** painting the hub's last picture from the very first paint (a snapshot). The hub's picture box is laid out by `screenfit.js` only once the page is in its ready state (the footer it measures is not shown before that), so a snapshot drawn earlier would sit in a different box and jump when the live canvas took over; making the two layouts agree means changing when layout runs, which was out of bounds. **Risks:** the copy takes 32 MB of the browser's storage (a browser may evict it, which just means a download; Safari clears script-written storage after a week without a visit); a copy corrupted inside the storage is shown for one frame before the re-check reloads the page (or, when the damage is in a table the menu needs, is hashed at once instead of shown); `BACK TO HUB` from a page is still a navigation (it takes the ~110 ms path above, not the instant back/forward-cache path). Not verified: a real phone, Safari, Firefox.
* **Tested in Chrome only** (headless Chrome 156 plus emulated phone and landscape viewports). No physical controller, no real phone, no Safari or Firefox, no screen reader was used.
* **The device tests are synthetic where a machine cannot do the real thing:** the controller is a scripted `navigator.getGamepads()`; the native file chooser and the native `<select>` popup cannot be opened in headless Chrome, so the tests hand a file to the file input (after the device activated it) and mouse / touch set a `<select>` by script; touch typing uses `Input.insertText` for the soft keyboard; a mouse-only journey types nothing (profile TRAINER, default team name, species found by scrolling the list).
* **A controller cannot use the operating system's file chooser** (a window outside the page). Importing a save with only a controller therefore works where the browser or the console hands the chooser to the pad, and otherwise needs another device for that one step; while a controller is the device in use the import screen says so ("A controller cannot open the file chooser: use the mouse, the keyboard or touch, or drop the file on this page"). Whether a real pad press counts as the user gesture a browser wants for opening a chooser was not tested (no physical controller was used).
* **Rebinding a key or button needs that key or button:** with only a mouse or a finger you can open the panel, switch the layout, cancel a capture and Reset, but not bind a new key.

## Known gaps

* **Online play is built** (`ONLINE.md`) and has these limits: an online battle is written into your record like any other (schema 4: its own ONLINE row, the opponent's name in RECENT; `ONLINE.md` says which profile and when), but it is **unrated**; **a reloaded page picks the battle up again**, but a tab closed for good costs the other player up to 60 s before they win, and a reload during the handshake is not resumable; there are no ratings, ladders or spectators; and **both browsers hold both teams**, because both run the engine, so a modified client could read the other team (it cannot read a choice before making its own, or steer the dice).
* **Doubles** are out of scope.
* **Not built, and not claimed:** the engine supports 688 of the ROM's 936 moves (and 173 of its 523 abilities, 662 of its 930 items), so a team using anything else is refused (see *What is approximate*); nothing elsewhere on this site links to the Arena yet, so it is reached at
  `/pokemonarena/`; there is no party-screen summary page, no BAG, no unlocks or experience (there is a battle record, see *Stats*) and no offline mode for the page itself (the game file is fetched from this site on a first visit, or after the browser evicted its copy, and kept in this browser; see *Coming back to the hub*). The move animations, the weather visuals, the music and the volume controls are each described in
  *What is approximate* and *Sound and music* with what is and is not done.
* **The Team Builder is a DOM page** (the ROM supplies every picture and icon, but form controls and labels are ordinary text), so it looks like a tool next to the ROM-drawn hub and battle screens, though the header, colours and buttons are the same on all three pages.
* **Every editor control is covered by the per-device journeys** only on the path a player takes (profile, team, species, nature, ability, item, four moves, EVs, an IV preset, save and reload, Test battle, import); controls outside that path (avatars, rename, delete, export, ruleset switches, the identity key) are covered by the editor page test with mouse, keyboard and script events but not by a controller-only or touch-only run.
* Players who clear the site's data in their browser lose their profiles: use Export in the Team Builder to keep a copy.
