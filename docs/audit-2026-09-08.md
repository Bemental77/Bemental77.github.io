## REFUTED — lead with these

### 4a. The drift gate green-lights a core with the SH4 JIT compiled out

`dreamcast/tools/verify_core_tree.sh` exists because eight ported files silently
reverted on 2026-09-07. Its checks are C1 *reverted to byte-identical upstream*,
C2 *missing from disk*, C3 *differs from upstream but untracked*, C5 *upstream
base moved*. C4 — *tracked file differs from outer HEAD* — is explicitly
**"REPORTED, never failed on"** (script header, and `:256`).

That leaves a hole the size of the incident it was built for. A file that is
tracked and still differs from upstream is invisible to C1 and C3, so **any
amount of damage short of a total revert passes**.

Demonstrated on the exact edit whose loss the header calls out. I removed only
the third port hunk of `core/build.h` — the `#if defined(__EMSCRIPTEN__)` block
holding `FEAT_SHREC DYNAREC_JIT` and `FEAT_AREC DYNAREC_JIT` — leaving hunks 1
and 2 (`CPU_WASM`, `HOST_CPU`) in place, then restored the file byte-for-byte
(`sha256 0acabfd7…` before and after, verified):

```
still differs from upstream (so C1 cannot fire)? YES

verify_core_tree: 34 tracked ported files under dreamcast/flycast-src
verify_core_tree: upstream base 4be8a484665fb5684ccb780ed2165018a679c622 (recorded: 4be8a48…)
verify_core_tree: 1 tracked file(s) differ from outer HEAD (in-progress work, not an error):
                  core/build.h
verify_core_tree: PASS — every tracked port edit is still applied, and every
                  upstream difference is recorded in git.
>>> verify_core_tree exit code = 0
```

That "PASS" line is false about the tree it just examined. The damage, confirmed
with the actual preprocessor rather than by reading (`cc -D__EMSCRIPTEN__ -E`, on
copies in `/tmp`, `DYNAREC_NONE = 0x40000001`, `DYNAREC_JIT = 0x40000002`):

```
build_ported.h     -> FEAT_SHREC 0x40000002   FEAT_AREC 0x40000002     (both JIT)
build_sabotaged.h  -> FEAT_SHREC 0x40000001   FEAT_AREC 0x40000001     (both NONE)
```

`HOST_CPU == CPU_WASM` matches none of the fallback branches at `build.h:80-93`,
so both features fall through to `DYNAREC_NONE`. That is **the SH4 JIT — the
entire project — plus the ARM7 dynarec**, silently compiled out, with both
`build_and_probe.sh:253` and `flycast_worker_link.sh:48` waved through because
they only test the exit code.

The gate catches a *total* reversion. It does not catch a partial one, a bad
merge, a truncated file, or a hand-edit that breaks a `#define` — and a partial
reversion is the more likely accident. `git diff` sees it (C4 printed the
filename); the gate declines to act on what it saw.

**Not fixed here — this audit does not touch product code.** The shape of a fix
is to make C4 fail by default when the build is not on a clean tree, or to record
per-file content hashes rather than only "is it upstream".

### 3a. PS1 memory cards do not persist

```
ps1/ps1Wasm/dist/wasmpsx_worker.js   IDBFS: 0   MEMFS: 48
ps1/ps1Wasm/dist/pcsx_ww.js          IDBFS: 33  MEMFS: 49
```

The worker — which is where the emulation core runs — is built with
`FS.filesystems={MEMFS}`. IDBFS is not merely unmounted; it is **not in the
build**. Its only FS setup is `FS.mkdir("/home/web_user/.pcsx")`. The core writes
cards to `/.pcsx/memcards/card1.mcd` (`strings wasmpsx_worker.wasm` →
`memcards/card%d.mcd`, `card1.mcd`, `card2.mcd`, `/.pcsx/memcards/`).

`pcsx_ww.js`'s 33 IDBFS hits are a red herring: its one mount is
`FS.mkdir("/cfg"); FS.mount(IDBFS,{},"/cfg/")` feeding `_LoadPADConfig()` — the
**pad configuration**, not saves.

So on PS1 a player's in-game memory-card progress is gone at reload. The page's
source comment (`ps1.html:876-880`) is scrupulously honest about this — "it does
not move a memory card" — but that honesty lives in a comment, not in front of
the visitor, and the headline claim is not qualified.

### 3b. The round-trip arm cannot fail

`state_export_import_test.mjs:298-311` exports to a file, asserts the file's
sha256 equals the stored sha256 (`:295`), imports that file back, re-reads **the
same key in the same profile**, and passes when the digest is *unchanged*.

The key already held those exact bytes. **An Import button wired to nothing
passes this arm.** The only thing standing between a dead import and a green
result is the toast regex at `:312`. The same file never clicks Load State, so
nothing in it asserts that an imported state restores a machine, and it never
leaves one browser profile — which is the entire purpose of Export/Import.

I built the discriminating version (`tools/audit_save_crossprofile.mjs`): profile

saves its own, different state; A's file is imported there and must **replace**

## Attacks that did NOT land — the work held up

These were the brief's own hypotheses. I tested each and they are wrong; saying so
is part of the job.

### The tests are not "BroadcastChannel-only"

`?net=local` swaps the **signalling** transport only (`lib/netplay.js:59-69`).
Every session in every test still builds a real `RTCPeerConnection`
(`:265`), a real offer/answer, real `addTrack`/`ontrack` media and a real
`DataChannel`. So the existing suites do exercise the WebRTC data path. What they
never exercise is the **broker** — see below.

### The guest is not looking at a live-but-empty track

The brief's known failure mode. The suite judges it with a 4x3 block-mean
signature quantised by `/8`, and its own comment records that the quantiser was
**widened from `/32` because Sonic Advance 3 failed at `/32`** — a threshold
calibrated on the failing case, which is exactly the sort of thing that should be
suspect. GBA's block-mean spread is 2.81 luminance levels against Genesis's 239:
an 85x weaker signal.

So I falsified the instrument. `tools/audit_netplay_guest_quality.mjs` suspends
the **host's** JS with CDP `Debugger.pause` — the emulator stops drawing, the
track stays live and connected, the picture genuinely freezes — and re-runs the
byte-identical sampler and the identical `>= 2 distinct` rule. Load 1.45:

| platform | presented (rVFC) | decoded (inbound-rtp) | judge, host running | judge, **host paused** | falsifiable |
|---|---|---|---|---|---|
| snes | 57.9 fps | **60.0 fps** | CHANGING (11 distinct, spread 42.4) | **FROZEN** (1 distinct, spread 0) | yes |
| genesis | 54.48 fps | **59.5 fps** | CHANGING (3, spread 2.56) | **FROZEN** (1, spread 0) | yes |
| gba | 27.19 fps | **49.8 fps** | CHANGING (5, spread 2.81) | **FROZEN** (1, spread 0) | yes |
| n64 | 18.86 fps | **20.8 fps** | CHANGING (6, spread 15.64) | **FROZEN** (1, spread 0) | yes |

The judge fails when it should. Its PASS is real evidence, GBA included.

And the question **nothing in any suite asked** — what frame rate does the guest
actually get — answers well: 60 / 59.5 / 49.8 fps, at 53–74 KB/s. N64 is the
outlier at 20.8 fps / 194 KB/s / 2 freezes.

One number in the suite output is misleading though: `mp_page_test` prints
`capture: canvas (3 frames/900ms)` for n64 inside a PASS line. That is a one-shot
**probe** used to pick a capture surface (`netplay-host.js:181-199`, accept at
`n >= 2`), taken while the core is still coming up — not the session rate, which
measures 20.8 fps. The acceptance floor being 2 frames/900 ms does mean a **2.2
fps** surface would be accepted and called good.

### The ±32766 quantisation does not break the Gauntlet composition

It is a real difference, and I measured it rather than reasoning about it. The
synthetic-gamepad path used by `dreamcast/docs/gauntlet-two-players/TASKS.md`
writes `axv(0) = 1.0 * 32767` → **+32767**. The netplay path quantises to a signed
byte and reconstructs: `q(32767) = 127`, then `127 * 258` → **+32766**
(`dreamcast.html:4309-4324`).

Both saturate the Dreamcast's 8-bit analog axis, so a 1-LSB-of-32767 difference
cannot change what the game reads. **The byte layouts coincide and the
composition holds.** Measured on the wire below.

## New finding: any session can be joined by a stranger

Not in the brief; found while reading the transport.

`lib/netplay.js:78` registers the host on the **public** PeerJS broker as
`bemental-<CODE>-h`, and `:103` accepts **every** inbound connection —
`peer.on('connection', wire)` — with no check on who is connecting. The room code
is the only secret: 5 characters over a 32-symbol alphabet = **33,554,432**
possibilities, in a fixed, globally-visible namespace on a broker anyone can query.

A third party who guesses or enumerates a live code gets the host's **live game
video and audio**, can **inject player-2 controller input**, and receives the
**save the host transmits at session end** (`sendSave`, `:410`). The only
rejection is a game-name mismatch (`:331`) — which I saw work correctly when my
own rig accidentally paired a `pso2` host with an `unknown` guest.

For a personal games site the impact is low: someone watches your Sonic run and
jiggles player 2. It is still an undisclosed property of a feature described as
peer-to-peer and private, and the same broker registration allows ID squatting —
pre-registering `bemental-XXXXX-h` makes a legitimate host's `new Peer(id)` fail.

## Ranked by risk to a real visitor

1. **A partial core reversion ships silently (4a).** Highest engineering risk in
   the batch. The gate's headline promise — "a drifted tree CANNOT silently
   produce a binary" — is false for every drift short of a full revert, and the
   worked example compiles out the SH4 JIT. Cost is a mystery-slow or broken
   Dreamcast build with a green gate above it.
2. **A ~13-minute half-shipped window on every deploy (5a).** Visitor-facing,
   recurs on every push, and 5 of the last 12 deploys were cancelled by the next
   push. Cheap to fix: poll the new files' live URLs after pushing.
3. **PS1 memory cards silently do not persist (3a).** A visitor plays Monster
   Rancher 2, saves in-game, reloads, and their card is gone. The truth is in a
   source comment; the visitor never sees it. Savestates *do* persist, so the
   page could say "use Save State — the memory card is not kept".
4. **No TURN server (1c residual).** Cross-device co-op will fail outright for
   users behind symmetric NAT, with no fallback and no diagnostic. Currently
   unmeasured — my two browsers shared a NAT.
5. **Export/import untested on gba, gamecube, dreamcast (3c)** and the n64 `.sram`
   never verified to reach the core (boot-only `LoadSram`).
6. **Strangers can join a session (new finding).** Low impact, zero authentication.
7. **A no-op import would pass the existing save test (3b).** The feature works —
   I proved it independently — but the guard would not catch a regression.
8. **`capture` accepted at 2 frames/900 ms.** Would ship a 2.2 fps stream and call
   it good. Not observed in practice; measured sessions ran 20.8–60 fps.

## Still unproven — honestly

* **Two real browsers driven to two moving Gauntlet characters (2c).** The byte
  path is now proven over WebRTC and the pixel path was already proven from a
  synthetic pad. The two have never been run as one sequence.
* **Real cross-NAT pairing.** Needs two networks.
* **The `ps1` co-op arm.** 451 MB disc; not reproduced by me.
* **iOS Safari.** The device matrix runs Chrome's engine everywhere; per
  `CLAUDE.md`, rows tagged `enginesDiffer` cannot clear real iOS.

## Method notes

* `tools/mp_page_test.mjs` and `tools/state_export_import_test.mjs` were read in
  full before being run, and both are unusually candid — the traps they document
  (rAF throttling in a background tab, `indexedDB.open` creating the DB the page
  needs, exact-hash-vs-codec-noise) are real and correctly handled. The criticisms
  above are about what they *omit*, not about sloppiness.
* The `build.h` mutation in 4a was applied and reverted inside a single shell
  invocation with a before/after `sha256` compare printed; `git status` for that
  path is clean.
* No product code was modified by this audit.
