## Where boot is stuck (cited)

**WASM probe last-observed state** (per `/tmp/dc-probes/vram-fastpath.log` and `/tmp/dc-probes/spg-walltime.log` tails):

- **pc = 0x8c02ab4c** at probe end (dispatch #3,819,000)
- **R14 = 0xa5323f44** (VRAM destination pointer mid-iteration)
- **R12 = 0x00200000** (outer-loop max count, set once before loop)
- **R13 = ~iter-counter** advancing toward R12
- **sr = 0x600000f0 / 0x600000f1** (MD=1, BL=0, IMASK=0xF — RB toggling between user/system bank)
- **0 exceptions in 30 s probe, 0 cache_miss**

## What the code at 0x8c02ab4c actually does (cited from /tmp/dc-blocks/0x8c02ab30.bin + sh4dis)

Disasm of `&mem_b[0]` at offset 0x2ab30..0x2ab6f, captured at runtime from OUR build's RAM (NOT from RedDream snapshot which is overwritten with game data at this address):

```
8c02ab4c: mov R15,R5            ; R5 = sp (src for memcpy)
8c02ab4e: mov #4,R6             ; R6 = 4 (byte count for memcpy)
8c02ab50: jsr @R11              ; CALL R11=0x8c02c15e — word-memcpy(R4=R14, R5=sp, R6=4)
8c02ab52: mov R14,R4            ; (delay) R4 = R14 (dst arg)
8c02ab54: add #1,R13            ; counter++
8c02ab56: cmp/ge R12,R13        ; T = (R13 >= R12)
8c02ab58: bf/s 0x8c02ab4c       ; loop back if not done (delay slot below)
8c02ab5a: add #4,R14            ; R14 += 4 (next 4-byte destination)
```

R11 callee at 0x8c02c15e (disasm from OUR-RAM dump at offset 0x2c150):
```
8c02c15e: shlr2 R6              ; R6 /= 4 (4 bytes / 4 = 1 word)
8c02c160: mov.l @R5+,R0         ; load word, src++
8c02c162: dt R6                 ; R6--, T = (R6 == 0)
8c02c164: mov.l R0,@R4          ; store word at dst
8c02c166: bf/s 0x8c02c160       ; loop (T==0 means R6 != 0)
8c02c168: add #4,R4             ; (delay) dst += 4
8c02c16a: rts                   ; return
```

**Net effect per outer iter:** `*R14 = *sp; R14 += 4; R13 += 1; if R13 < R12 loop`. With R12=0x200000, R14_start=0xa5000004 → fills **8 MiB of PVR VRAM** with the 4-byte word at sp, written one word at a time.

**Loop end:** R14 reaches 0xa5800004; R13 == R12; bf doesn't take; function epilogue (rts at 0x8c02ab68).

## Why we don't reach the end in the 30 s probe (cited)

R14 trajectory in `/tmp/dc-probes/spg-walltime.log`:
- R14 start: 0xa50003e8 (iter ~250)
- R14 at probe end: 0xa52e1cb0 (iter ~755 K)
- **39 % of 8 MiB filled**

Steady-state cost per outer iter ≈ 4 dispatched blocks × ~5 μs/dispatch = ~20 μs. Total: ~42 s wall for 2.1 M iters. Probe was 30 s — runs out before natural completion.

## This is NOT a wedge (cited from native oracle)

Per `/tmp/native_realbios.log` (native flycast libretro with `--enable-log`, 30 s wall on the same PSO disc):
- 754 `[DYNAREC]` compile events
- Last compiled PCs include **0x8C378CD6, 0x8C378CE4, 0x8C3C2E20, 0x8C3C2ED4, 0x8C3C2EE4** — PSO game code loaded ~3-4 MiB into RAM
- 0 errors, REIOS init clean, VMEM normal

**Native PSO completes the VRAM fill and reaches game code at 0x8C378xxx-0x8C3C2xxx in the same 30 s**. The WASM build is **not stuck** — it's slow.

## What's shipped this session (uncommitted on ps1Edge)

1. **Memset byte-loop fast path** (`bementalJIT/guests/sh4/wasm_emit.cpp` `detectMemsetByteLoop` + `emitMemsetFastPath`). Detects 4-op SHIL shape (writem size=1 + add#1 + readm size=4 + setae) on self-loop blocks; emits `memory.fill` for area-3 RAM range. Cleared 0x8c0133f4 BSS-clear wedge in <1 dispatch.

2. **Data count section + `op_memory_fill`** in `bementalJIT/include/bementalJIT/wasm_module_builder.h`. Required by wasm bulk-memory spec when modules use memory.fill/copy/data.drop.

3. **Block-bytes hex dump hook** in `dreamcast/flycast-bridge/rec_wasm.cpp`. One-shot postMessage emitter for a hardcoded set of vaddrs (0x8c0133f4, 0x8c02ab4c, 0x8c02c160). Probe greps `[blockdump]` lines; Python decodes hex to /tmp/dc-blocks/.

4. **SPG raise wall-time gate** in `dreamcast/flycast-bridge/rec_wasm.cpp:1296`. Replaced `(s_spg_tick & 0x3F)` JIT-throughput-coupled gate with `emscripten_get_now()` ≥16 ms gate (~62.5 Hz). The previous gate gave 7.5 Hz wall instead of documented 250 Hz because s_spg_tick advanced at JIT-drain rate, not wall rate. **THIS was the real boot blocker**; not "throughput."

5. **Area-4/5 (VRAM) wasm-direct fastpath** in `bementalJIT/guests/sh4/wasm_emit.cpp` shop_writem. Reads `g_vram_lin_base` (set by bridge at SH4 init to `(u32)&vram[0]`) and emits `i32.store* at LOCAL_RAM + vram_offset` for addresses in areas 4/5. Bypasses the sh4_write32 import callback for PVR VRAM writes. Modest 8 % per-iter speedup on the 0x8c02ab4c stall (per-word write was not the dominant cost).

## What I now know that I didn't at start of session

- The boot path *past* the VRAM fill leads to **0x8C378xxx-0x8C3C2xxx game code** (cited from native).
- The dominant per-iter cost in our WASM is **dispatcher round-trip per block** (~5 μs), not per-word memory writes. The VRAM area-4/5 fastpath confirmed this — eliminating the slow-path callback gave only 8 % improvement.
- Three "blockers" this session, in order, were:
  1. 0x8c0133f4 BSS clear (memset, fixed by `memory.fill` pattern match)
  2. SPG raise rate coupled to JIT throughput (fixed by wall-time gate) — **this was the actual progress unblocker**
  3. 0x8c02ab4c VRAM fill (legitimate slow code; not blocked, just slow)

## What I do NOT yet know

- Whether the 0x8C378xxx / 0x8C3C2xxx region reveals further blockers in our WASM (we never reach it). Could be more polling stalls, more slow byte-strides, or wedge-class bugs.
- Whether block linking (return_call chains for the 4-blocks-per-VRAM-iter case) is the right next lever, or pattern-match the outer loop, or accept the slow boot until other paths complete.
- Whether native flycast eventually reaches the title screen in this same probe duration (would need longer native run + frame-event log).
