# Independent research: why the MP4 board scene is CPU-bound, and where the multiple is

**Scope & method.** Second-opinion analysis of `Bemental77/Bemental77.github.io` (branch `prod`, examined 2026-08-05) done *without* reading the project's own CLAUDE.md / research_findings.md / webAssemblyFindings.md / STATUS.md / docs. Evidence base: direct reading of the JIT (`bementalJIT`, `guests/powerpc-next`), the dispatch/runtime layer (`JitWasm.cpp`, `block_cache.cpp`, `dolphin_jit_wimports.cpp`, `EmscriptenWorker.cpp`, `CoreTiming.cpp`, GX path), the live page config (`gamecube.html`), an exhaustive census of dated measurement comments embedded in the source, current V8 source (flag defaults, inlining, tiering), and prior art (v86, CheerpX, QEMU-wasm, flycast-wasm, WATaBoy). Six candidate recommendations were then **adversarially verified** against the source by independent passes; verdicts and the two live correctness holes they uncovered are in §6-§7.

## 1. The live system, as actually configured (several docs-era beliefs are stale)

- **Executor:** `window.__dolphinDualCore = true` is hardcoded and `__dcTakeover` is unset (`gamecube.html:330-344`), so the ppc-worker takeover is **disabled**. The guest CPU runs on Dolphin's EmuThread pthread in `JitWasm::Run()` (`JitWasm.cpp:206-631`): one `chain_dispatch` EM_ASM crossing per inner iteration wraps `bem_chain_loop_c`, which `call_indirect`s into block modules; blocks then tail-chain **inside wasm** via `return_call_indirect` on the shared table at a **99.66% hit rate, 4.8M tail-calls/s** (PM51 census, `ppc_emit.cpp:71-73`). The entire ppc-worker fastpath corpus (mailbox round-trip counts, check-exc fastpath, mem1-direct, 19%-of-wall gather gate) describes a **retired execution path**.
- **JS boundary:** all 13 imports the JIT'd blocks call (`ppc_read*/write*`, `ppc_interp`, `ppc_check_exc`, `ppc_hle_check/fire`, `ppc_msr_updated`, `ppc_gather_drain`) are **cross-instance wasm→wasm calls, no JS frame** — bound once via the thunk-resolve in `block_cache.cpp:336-440`. Remaining JS-membrane crossings on the hot path: the one EM_ASM per chain entry, `compile_raw`'s sync `new WebAssembly.Module/Instance` per block, seal/relink EM_ASMs, and 2× `emscripten_get_now` per `CoreTiming::Advance` (TEMP timer, `CoreTiming.cpp:361-380`).
- **GX:** the GPU *decode* does not run on the EmuThread, and not on the parked gpu_thread either — it runs in `RunGpuLoopSlice` on the **proxied-main (WebGPU device) thread**, pumped from `retro_run` (`Fifo.cpp:336-522`; `JitWasm.cpp:291-294`). The "gpu_thread sees a different WebAssembly.Memory" theory in `Fifo.h:70-82` was **disproven in-tree** on 2026-07-22 (`fifoAddrGpu==fifoAddrCpu`, `gamecube.html:347-352`); the real causes were an unprepared `BlockingLoop` that never woke (`Fifo.cpp:104-117`) plus a genuine missing acquire/release pair (PM37, `Fifo.cpp:420-433`). `DrainFifoOnCpuThread` has **no caller** — dead vestige. The EmuThread's only GX work is gather-pipe *production* (per-word slow-arm import + per-32B-chunk accounting). An idle GPU thread is therefore **by design**, not a recoverable resource; the win is entirely inside the EmuThread's per-block overhead.
- **HLE:** zero patches installed in the live build (`kInstallLegacyPatches=false`, `EmscriptenWorker.cpp:1226-1230`) and `g_hle_hook_query` is wired at `JitWasm::Init` (`JitWasm.cpp:126-128`), so the catastrophic per-op HLE prologue tax (~18× bookkeeping blowup) is **not** being paid — `ppc_hle_check/fire` are dead at runtime.

PROMOTION IS OFF, AND THAT MAKES ALL RUN-FUSION DEAD CODE.** `unsigned char g_bem_promote_enabled = 0;` at `block_cache.cpp:233` (the cited `:132-137` is the `g_bem_rtag`/`g_bem_rslot` declarations, not the flag). Disabled by commit `a8e1d97` as a **measured board REGRESSION — OFF +36% vs ON** (peFrames 1814 vs 1337, confirmed in the user's real Chrome). The chain: the promote-ring prologue emits only under `if (g_bem_promote_enabled && region_gen < 0)` (`ppc_emit.cpp:1035`) → nothing reaches `g_bem_promote_ring` → `promote_hot` never accumulates → `region_seal` (`block_cache.cpp:2042`, sole trigger `:2689`) is never called → **run-fusion never executes — integer fusion included.**
  **MEASURED CONSEQUENCE:** seal-census cells `0x026B3430/3434/3438/343C` all read **0** at t≈180s across three runs with live scenes (`drawn` 8.4-18.6/s, `xpc` in the PSMTX range) at loads 41, 24 and **15** — so not a load artifact. Any fusion A/B run today compares two identical configurations.

## 2. The corrected cost model — it is not "a thousand cuts"

Per-guest-instruction accounting from the emitters (emitted-wasm-op counts, verified in `ppc_emit.cpp` / `jit_load_store.cpp` / `cr_encode.cpp` / `reg_cache.cpp`):

| Item | Cost | Where |
|---|---|---|
| A plain ALU op (`add`), mid-block | **4 ops** | `jit_integer.cpp:291-308` |
| `lwz` fast path (EA + guard + bswap + commit) | ~30 ops + 3/dirty-GPR flush | `jit_load_store.cpp:119-513` |
| Rc=1 / compare CR materialization (eager) | 28-30 ops | `cr_encode.cpp:154-181` |
| Block prologue (downcount + live-in loads + promote-ring counter) | ~19-32 ops | `ppc_emit.cpp:887-973` |
| Block terminal: service bail (~30) + vector guard (~16) + probe (~28) + flush | **~77 ops** | `ppc_emit.cpp:150-380` |
| Register state at every block edge | full GPR/FPR spill + successor reload | `ppc_emit.cpp:143-145`, `reg_cache.cpp` |

Typical hot blocks are **3-9 instructions** (`ppc_emit.cpp:930-932`), so a 5-instruction block executes ~124 ops of which ~20 are real work: **~25-30 wasm ops per guest instruction all-in, of which 4 are the actual ALU**. The thread-level decomposition agrees: guest-body ≈ 55.8% (which *includes* in-block prologue/epilogue overhead), chain-head dispatch loop ≈ 25.4% self-time (2026-06-23 baseline), cross-module edge sequence ≈ 12.9% (PM51), `Advance` + misc the rest.

**The reframe:** the "~18% emitted code / 12.8% dispatch / ~10% JS boundary" attribution makes the cost look scattered. It isn't. One structural fact — **architectural state round-trips through memory at every 3-9-instruction block boundary, surrounded by ~96 ops of fixed bookkeeping** — is what all three buckets are made of. The service-bail + vector-guard execute 362.5M times per 75s to catch a bail that fires 0.32% of the time. The in-code estimate for the per-entry prologue+call tax alone is **"~40% of thread"** (`block_cache.cpp:166`). Roughly 70-80% of EmuThread time is block-boundary overhead in one form or another. That is a single target, not a thousand cuts — and cutting it is what every successful wasm DBT converged on.

One sizing nuance the census exposes: the *tail-call instruction itself* is cheap — microbench 9.82ns cross-module vs 6.64ns intra-region ≈ **~1.5% of thread** as the pure call-cost ceiling (`ppc_emit.cpp:111-121`; cross-gen re-entry via global-table wrappers "measured as free", `ppc_emit.cpp:119-121`). The 12.9% census figure is the whole edge *sequence* — predicate + probe + spill/reload around the call. So module-merging **per se** buys little; killing the per-edge work and the state round-trip is where the 12.9% (and much of the 55.8%) actually lives.

The wasm-vs-native floor is real but is *not* what caps the system today: bswap 11 ops vs native `MOVBE` (`jit_load_store.cpp:213-231`), eager CR ~28 ops vs free x86 flags (DCE'd by TurboFan when dead, elided via `crDiscardable`), FTZ/NaN ladders now config-gated to native parity (PM46/PM59/PM60). Those floors matter at the end of this road, not yet.

## 3. What V8 actually gives and refuses (checked against V8 `main`, Aug 2026)

- **No cross-module inlining, ever.** `InliningTree` refuses imported functions; candidates/feedback are same-module only. One-module-per-block forfeits *all* interprocedural optimization permanently.
- **Same-module inlining is generous at this block size:** feedback-driven, `--wasm-inlining-max-size` = **500 wire bytes** per callee (a 3-9-instr body is well under), graph-growth ~3×, budget ~5000 nodes, speculative `call_indirect`/`call_ref` inlining up to **4 targets per site** (M137+, with deopts). A central dispatch site fanning to thousands of blocks is megamorphic → never inlined; per-predecessor direct/indirect edges are exactly the inlinable shape (what the N-fn gens + PM54d direct edges already exploit).
- **Every fresh module starts cold:** Liftoff + lazy + its own 13MB tiering budget + empty feedback; **no OSR** mid-activation. ~16K per-block modules = ~16K cold starts and ~16K× code-space/jump-table overhead (V8's estimate: Liftoff ≈ 4× wire bytes + 56B/fn). Only byte-identical modules share via the isolate cache.
- **Tail calls work in both tiers** — the chaining design is sound on this point.
- **Branch hinting** is in V8 main's always-enabled feature set (Chrome stable imminent; Firefox default-on announced). The module builder has hint plumbing (`op_if_hinted` / `branchHints()`, `wasm_module_builder.h:739-751`) but it is **entirely unused** — zero call sites, no custom-section emitter (§6.3).
- **Sync compile** ≤8MB is legal on-thread; persistent code caching applies only to streaming-from-HTTP ≥128KB — runtime-generated modules never cache across loads.
- **Multi-memory, relaxed SIMD, Memory64** are shipped; relaxed SIMD is already used (`f32x4.relaxed_madd`); multi-memory/Memory64 buy nothing here (bounds checks already elided; the guard is a 4-op MMIO classifier, not a bounds check).
- **Prior-art convergence** (v86, CheerpX, QEMU-wasm, flycast-wasm, all independently): compile at **region granularity** (page / hot-region / TB-batch / per-frame batch), one shared memory + table, dispatch kept **inside** the module, minimal import crossings, guest registers in **locals** across the region (flycast measured locals-vs-context-loads at **3-5×**). WATaBoy is the cautionary tale: per-block modules + `call_indirect` dispatch ≈ only 1.2× over an interpreter.

## 4. Re-reading the "inlining budget ceiling"

"Bigger translation units stop paying off because of V8's inlining budget" is true of exactly one strategy: *emitting small functions and relying on V8 to merge them*. The budget does not cap **emitter-side merging** — V8 optimizes a large hand-merged function fine (limits: 7.6MB body, 50K locals — orders of magnitude away). What about the in-tree evidence that merged regions lose? The adversarial re-examination (§7.6) found it much weaker than the tree's own "three consistent losses" framing:

- **step-0 (−38%, 24.6 vs 39.7 gc/s):** confounded — merged bodies were **Double-only**, forfeiting the PM44/46/47 singles arms; the code itself attributes the loss to this (IDCT 7.3×→15.4×, `block_cache.cpp:156-166`).
- **"07-16 (−8%)":** the only −8% record in-tree is dated **2026-07-13 — before the merged builder existed** (`block_cache.cpp:117-122` vs `:129`), measured on the retired region-FIRST EM_ASM dispatch at ~5% hit rate. It is not evidence about the merged shape.
- **step-1 (34.4 vs 39.7, the one clean loss):** carried four identified **hub artifacts**, all in-code: (1) the PM47 self-loop fast protocol is `!merged`-gated, so merged IDCT loop arms re-ran a ~160-op/reg singles rebuild per warm edge (`ppc_emit.cpp:995-1000, 1029-1045`); (2) per-warm-edge lap-counter + `entry_sel` global traffic (`ppc_emit.cpp:280-294`); (3) FPR prologue reloads re-run on every re-entry — only GPRs were resident (`ppc_emit.cpp:1079, 1114`); (4) `jit_branch.cpp` has **zero** merged-region support — every mid-block coalesced taken exit host-bounces out of the region (`jit_branch.cpp:43-60`).
- The "256-arm br_table phi-merge defeats regalloc of 152 locals" theory is an explicit *hypothesis* attached to a **neutral** A/B (`block_cache.cpp:167-171`); the merged `$region` unconditionally declares all 152 locals + a 32-GPR activation pad (`ppc_emit.cpp:2107-2126`); nothing in-tree isolates locals-count vs arm-count.
- **No structured-CFG merged shape has ever been tested.** The one structured datapoint — `int_fused` integer self-loops in a real wasm `loop` — shipped and stayed on. There is no A/B of natural-loop/if-nested multi-block regions with per-segment guards, trimmed locals, and in-region branch handling.

So the honest status is: the dispatcher-hub shape lost once cleanly (with four named artifacts); emitter-merged structured regions — the shape CheerpX/v86 actually use — are **untested here**, and V8 imposes no budget on them. The tree's own current bet (N-fn gens + intra-gen direct `return_call`, PM54c) is the other defensible direction and is live with no recorded result yet. These two are complementary: N-fn+direct-edges keeps V8's per-function optimization and gets selective inlining; structured regions get state residency. Both attack the same ~40%-of-thread prize.

## 5. Immediately available wins (no architecture change)

1. **Strip the TEMP instrumentation still on the hot path:** `slowmem_audit` volatile RMW on **every** import call (`dolphin_jit_wimports.cpp:102-114`); AdvTimer `emscripten_get_now` ×2 per `Advance` (`CoreTiming.cpp:361-380` — this call class measured **5.4% of the JIT thread** before being gated off elsewhere, then re-added here); ~9 volatile diag publishes per 32B gather chunk + 2 per GX word (`GPFifo.cpp:95-186`, `CommandProcessor.cpp:382,422`); per-slice diag RMW (`JitWasm.cpp:269`); and the promote-ring profiling prologue still emitted into every **non**-region block (**15-40% of executed ops on 3-9-instr blocks**, `ppc_emit.cpp:924-932` — paid by the unpromoted tail of the board's ~13.9K live blocks; board coverage: top-512 = 77.8%, top-2048 = 97.9%).
2. **Re-profile before anything else.** PM62 (2026-08-05 — the day of this research) made the board's dominant interpreter fallbacks native: fcmpu 21.2M + fcmpo 15.1M + cror-class 8.9M + frsqrte 8.1M + fsel 3.3M + fres 1.7M per run (`jit_floating_point.cpp:91-188`, `jit_compare.cpp:124-131`). The 5-6fps figure likely predates it. Then take the next `WIMPORT_INTERP` census.
3. **Fix the two live correctness holes the verification pass found** (they gate everything in §6):
   - **PM54d direct edges are unguarded after evict.** The intra-gen bucket probe is gen-tag-guarded, but the PM54d terminal `ctx.PC == direct_pc → return_call fidx` edge has **no tag/gen term** (`ppc_emit.cpp:243-253`). Gens are immutable; per-PC evict (icbi/SMC/deopt) clears buckets only — a same-gen predecessor keeps tail-calling the **stale body** forever (`block_cache.cpp:1153-1159` documents that per-PC evict was sufficient only *because* edges were runtime-resolved; PM54d silently reintroduced baked edges). With PM26 deopt this becomes a permanent re-deopting, slice-killing edge (`JitWasm.cpp:504-517`, threshold at `block_cache.cpp:219-222` effectively-never).
   - **PM54f fusion-extent invalidation hole.** Run-fusion splices successor instructions inline into predecessor functions, but `InvalidateICacheRange`/`m_block_guest_end` track only each block's own contiguous span (`JitWasm.cpp:157-178, 692-693`) — an SMC write to a fused-in tail evicts the successor PC but leaves the predecessor's inline copy running. Needs multi-range extents or a reverse pc→fused-host index.

## 6. The structural path to a multiple (adversarially verified)

Ordered by risk-adjusted value. Expected magnitudes are bounded by in-tree measurements where they exist; the PM53 lesson (`ppc_emit.cpp:58-69` — two "obvious wins" measured −9/−11%) means every one of these needs a live A/B.

**6.1 Edge-check diet — WEAKENED→refined, the cheapest real lever.** Collapse the ~30-op service predicate to a downcount-only sentinel (`load downcount; br_if <=0`), keeping the **vector-page guard in-wasm** (its removal is refuted: `rfi` is a bare interp fallback whose block can `return_call_indirect` straight into a cached vector-page block with EE=0 — the exact recorded 2026-07-09 ISI-at-0x594 crash; the guard is marked PERMANENT, `ppc_emit.cpp:216-226`, `jit_branch.cpp:530-537`). Preconditions from verification: raisers must use the existing `ForceExceptionCheck(0)` idiom, never raw `downcount=0` (raw zero time-warps CoreTiming — recorded harm at `JitWasm.cpp:571-580`; the idiom already exists at `CommandProcessor.cpp:418-419,460`, so gather-pipe backpressure already *is* this pattern); add a post-`rfi` `CHECK_EXC` mirroring mtmsr's (`jit_system_registers.cpp:320-323`) or masked-pending delivery slips a full slice (recorded compat hazard class, `CoreTiming.cpp:523-526`); and keep the Exceptions poll whenever `cpu_owner==1` since the worker-era design forbids cross-thread downcount writes (`CoreTiming.cpp:388-402`) and the prologue downcount RMW is non-atomic (`ppc_emit.cpp:913-918`). Net: ~46 → ~21 ops per edge × 4.8M/s, plus the same diet inside `bem_chain_loop_c`.

**6.2 FP/paired-single fusion at seal — WEAKENED→refined, the biggest emitter-side lever for the board.** The board's hot code is FP (Hu3D), and run-fusion currently fuses **FP-free records only**, so the hottest paths get no fusion at all. Extending it is directionally sound with three named preconditions: (1) exclude self-loop/assumed-set blocks until the PM47 fast-loop protocol is ported to the fused surface (it is `!merged`/per-block-gated today — the exact step-1 artifact); (2) guard single/double speculation **per segment** rather than unioning FPR live-ins across the fused body — a fused MusyX-side callee would otherwise route the whole body to the Double arm per entry, dynamically re-creating step-0's pessimization (`ppc_emit.cpp:975-1020, 1644-1714`); (3) land fused-extent SMC tracking (§5.3) first. MSR.FP-across-seams is safe (mtmsr is FL_ENDBLOCK → never fused; `block_cache.cpp:1779-1789`), and the `bl`-seam guard is compile-time-predicted with a byte-equivalent mispredict path (`ppc_emit.cpp:1340-1374`) — no RAS hazard.

**6.3 Branch hints — WEAKENED→scoped, cheap but not free.** The bias data is real (service bail 0.32%, vector arm literally 0 fires, all arms are hintable `if`s in the right direction), but nothing is collected today (`op_if_hinted` has zero call sites), the builder lacks a custom-section API and emits Code last (section must precede Code — needs two-pass or splice), and N-fn gen modules need per-funcidx hint carrying across the body-splice boundary (`ppc_emit.cpp:1859-1866`). Exclude the HLE arms (Replace-type hooks return 1 ~100% of the time — the "cold" hint inverts there) and forget "deopt arms" (stale — PM44 v9b replaced them with a bimodal per-entry select that must not be hinted). Expect low-single-digit %, accruing only post-tier-up.

**6.4 Finish and harden the N-fn trajectory (the tree's own bet) — the *as-stated* "batch everything" version is REFUTED.** Making batched modules the primary path for ALL blocks loses on the tree's own evidence: ring-arrival (discovery-order) sealing measured **−25%**; high-cadence sync seals measured **−27%** with ~12s freezes; seals are necessarily synchronous on the EmuThread (PM53c: microtasks never drain there); and gens are append-only with a 24×256=6144-PC cap vs a 13.9K-block live set, behind a 16384-block `clear()` that wipes every gen at once. What survives: **complete the PM54c acceptance run** (top-K, post-boot, capped — live with no recorded result), close the §5.3 eviction holes (gen-tag/epoch term on PM54d direct edges; fusion-aware invalidation), then lift the capacity wall (more gens or LRU gen recycling instead of global `clear()`; the board wants ~2048 promoted PCs for 97.9% coverage).

**6.5 The open structural experiment — structured-CFG merged regions (SURVIVES as a hypothesis worth one clean test).** Given §4, the highest-information experiment in the whole space is: pick the top 2-3 board loop nests, emit them as **one function each with natural wasm loop/if structure** (no br_table hub, no entry_sel), per-segment single/double guards, liveness-trimmed locals (the fixed 152-local/8-group splice contract is an engineering cost to break, `ppc_emit.cpp:2107-2113`), in-region conditional branches (today `jit_branch.cpp` host-bounces every taken mid-block exit), side exits via the existing global-table chain. That is the CheerpX shape, it is the only untested quadrant, and the int_fused precedent (the one structured shape ever tried) shipped as a win. Keep the sync-compile discipline (one Liftoff-tier compile per region is the accepted cost, `block_cache.cpp:1992-1994`) and A/B it scene-matched.

**6.6 Negative results (do not spend time here).**
- **Off-thread compile/instantiate is platform-impossible — REFUTED.** `WebAssembly.Table`/`Instance`/exported functions are per-agent and cannot be shared or posted between workers; under Emscripten pthreads each thread has its own table object, and this tree already documents the per-thread `Module` isolation class (`block_cache.cpp:341-353`, `worker_funcs.js:91-98`). A pump-thread-instantiated block can never be `call_indirect`ed by the EmuThread; the only shippable artifact (`WebAssembly.Module`) needs an EmuThread event-loop task that PM53c proves never runs. Sync EmuThread compiles are the settled, in-tree-accepted design.
- **Raising the straight-line block cap** — PM52 already proved WASH (hot set is terminator-bounded).
- **Per-edge state passing through tail-call args** — the PM53 spill-pack family measured −9/−11% twice with an explicit "DO NOT RE-TRY".
- **First-compile fusion / branch-following as a flag flip** — `m_enable_branch_following` is a dead flag (declared, referenced nowhere); this is a genuine port of Dolphin's branch-following into the analyzer, and it lacks the batch-local profile facts the seal-time fuser depends on. Legitimate future work, not a quick lever; PM52's memo also warns bigger first-compile blocks worsen the cold-compile transient.

**Sizing the stack honestly:** hygiene (§5.1) + edge diet (6.1) + hints (6.3) plausibly recover ~15-30% combined; FP fusion + a working promoted tier at real coverage (6.2/6.4) is where the in-code "~40%-of-thread per-entry tax" gets structurally attacked — that is the multiple, worth 2-3× on the CPU side if the fused/resident shape wins its A/Bs; the structured-region experiment (6.5) is the highest-variance bet on top. 60fps on the board almost certainly needs the structural tier *plus* the post-PM62 baseline; ~30fps is the realistic intermediate milestone. Every step needs the live-A/B discipline this codebase already practices better than almost any tree I've read.

## 8. Corrections to the prompt's framing

1. **"GPU thread sits ~80% idle"** — true but by design: GX decode lives on the proxied-main device thread; the gpu_thread is parked; the EmuThread carries only gather-pipe production. There is no GPU-offload win hiding here. (Neither the 5-6fps nor the 80%-idle figure appears in-tree; both presumably come from live profiling — re-measure post-PM62.)
2. **"JS-boundary calls ~10%"** — in the live build the block imports are wasm→wasm. That bucket is really the cross-instance call *sequence* + one EM_ASM per chain + the TEMP get_now pair. Naming it "JS boundary" points at the wrong fix; the boundary that matters is cross-instance, and the expensive part is the ops around the call, not the call.
3. **"Each fix buys 10-25%, never a multiple"** — the census supports the observation, not the conclusion. Every fix so far shaved a *symptom* of block-boundary overhead; the boundary itself (state round-trip + ~96 fixed ops per 3-9 instructions, ~40% of thread by the tree's own estimate) has been attacked as a unit exactly once, via one confounded experiment on a known-pathological shape.
4. **"The structural multiple is capped by V8's inlining budget"** — the budget caps only inliner-dependent merging. Emitter-side merged regions are uncapped and untested here; the N-fn+direct-edge path (the tree's live bet) additionally gets real same-module inlining at ≤500 wire-bytes/callee. The ceiling, where one exists, is the wasm-vs-native floor (bswap, CR materialization, no trap-and-patch fastmem) — and the system is nowhere near it yet.
